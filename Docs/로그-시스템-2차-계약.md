# 로그 시스템 2차 계약

작성일: 2026-10-31. 1차의 저장·봉투·ID 계약을 유지하고 실제 Game 세션과 웨이브 경계를 연결했다. Unity 실행 검증은 사용자 확인 대기다. 틱별 위치/적 수, 전투·탄약·슬롯·상점 상세 수집은 이번 범위에 포함하지 않는다.

## 초기화와 시간 소유자

`GameManager.Awake`의 기존 모델·초기 무기 구성을 유지한다. `Start`에서 `InitializeLogging`을 호출하고 기존 첫 웨이브 대기 코루틴을 시작한다. 생성 조건은 Application.isPlaying이며 GameManager가 속한 씬 이름이 실제 `SceneNames.GAME`인 경우다. 초기화는 인스턴스당 한 번이다. Preload/Title, 프리팹 저작과 테이블 로드는 플레이 로그를 만들지 않는다.

`GameManager.Logging.cs`는 기존 GameManager의 partial 확장이며 새 컴포넌트/씬/프리팹 연결은 없다. `LogUnityAdapter.CreateSession()`이 설정·persistentDataPath·초기 Time.fixedDeltaTime을 복사하고, `LogGameLifecycle.Start()`가 session_start를 한 번 기록한다. `GameManager.Telemetry`로 해당 인스턴스의 생명주기와 `Telemetry.Session`에 접근할 수 있다. Title→Game은 새 GameManager와 새 sessionId를 사용한다.

이후 GameManager의 단 하나의 FixedUpdate가 `telemetry.AdvanceFixedUpdate(Time.fixedDeltaTime)`을 호출한다. 서비스 내부의 1차 시계만 누적한다. 상점에서도 누적하고 FixedUpdate가 없는 정지 구간은 누적하지 않는다. 후속 수집기는 이 누적 이후 같은 `Session.ElapsedSeconds`를 읽어야 하며 `LogUnityAdapter.AdvanceFixedUpdate`나 서비스의 시간을 별도로 더하지 않는다. 현재는 고정 시계와 fixedDeltaTime 변경 기록만 연결했고 위치/적 수 틱 레코드는 아직 생성하지 않는다.

session_start payload는 utc, buildVersion, buildGuid, dataVersion, dataFingerprint, mapId, fixedDeltaTime이다. Application.version/buildGUID 및 실제 씬 경로를 복사하며 빈 값은 null이다. 별도의 데이터 버전은 없으므로 dataVersion은 null이다. dataFingerprint는 당시 TableManager가 보관한 13개 테이블의 값을 고정 순서로 직렬화한 SHA256이다. 원본 JSON 파일 바이트나 Git 커밋 해시라고 해석하지 않는다. 지문 계산 실패 시 null과 제한된 진단을 남긴다.

## 웨이브와 보상 경계

실제 StartWave가 진행 상태를 설정하고 WaveController.Begin을 수행한 뒤, 기존 WaveStarted 구독자 호출 전에 `BeginWave`를 연결했다. wave_start는 확정 WaveSpec의 번호·제한 시간·예정 적 종류/수·시대·적 무기와 그 시점의 플레이어 스냅샷을 가진다. 예정 종류는 수가 양수인 종류만 포함한다. 입력 객체는 값으로 복사하여 이후 교환·보충으로 시작 상태가 바뀌지 않는다.

EnemyKilled는 WaveController가 실제 살아 있는 목록에서 적을 제거한 경로만 사용한다. 기존 GameManager 처치/보상 처리 뒤 생명주기의 처치 수를 올린다. WaveController.Stop의 강제 제거는 이 이벤트를 생성하지 않으므로 처치 합계에 더하지 않는다.

OnEnemiesCleared는 `enemies_cleared`를 한 번 기록하고 웨이브는 열린 상태로 둔다. payload는 clearedElapsedSeconds, waveElapsedSeconds, kills다. 조기 전멸만으로 보상을 주거나 완료 요약을 출력하지 않는다. 기존 EndWave의 시간·생존·중복 호출 방지 조건을 유지한다.

정상 완료의 연결 순서:

1. 기존 중복 완료 가드/lastCompletedWave 갱신.
2. 적 정리 전 `CaptureAliveSnapshot`을 값으로 확보.
3. 기존 waves.Stop → 회복 → 돈 보너스 → 슬롯 진열 갱신.
4. 보상 적용 후 플레이어 상태로 `CompleteWave` 및 wave_summary.
5. 기존 WaveEnded → Shop 전환과 기존 UI 이벤트.

정상 wave_summary의 bonusPaid/healthRestored는 GameManager가 실제 완료 처리로 확정한 WaveBonusPaid/WaveHealthRestored다. 실제 보너스가 0이면 숫자 0이다. 중단 요약은 rewardsApplied=false, bonusPaid=null, healthRestored=null로 두어 미지급과 구분한다.

wave_summary payload는 summaryId/revision/status/reason, startedElapsedSeconds/endedElapsedSeconds/waveElapsedSeconds, plan/startPlayer/endPlayer, enemiesBeforeCleanup, kills, clearedElapsedSeconds/clearDurationSeconds, rewardsApplied/bonusPaid/healthRestored, summaries다. 첫 원본 revision은 0이며 summaryId는 1차의 `<sessionId>:wave:<번호>`다. 미전멸 시 전멸 시각은 null이다. 정상 status는 completed/reason은 time_limit, 중단 status는 interrupted다. 하나의 웨이브를 정상/중단 양쪽으로 중복 마감하지 않는다.

## 스냅샷과 사망

플레이어 스냅샷은 실제 PlayerHealth의 체력·월드 x/y/z, 지갑, 활성 슬롯, 모든 휴대 무기 개체/탄종/장전탄/파츠, 탄종별 공유 예비탄과 실제 최대량을 복사한다. 실제 PlayerWeapon.Hand(0)/Hand(1)을 각각 right/left로 연결하고 양손 활성 시 activeHand는 both다. 휴대만 하는 무기는 hand=null/active=false다. 무기 ID는 1차의 참조별 GetWeaponId를 사용해 바닥 왕복/슬롯 이동 시에도 유지한다. 원본이 없는 값은 null이며 장전탄 0은 실제 0이다. 별도 바닥 무기 전체 목록은 수집하지 않는다.

`WaveController.CaptureAliveSnapshot(Vector3? center, float? radius, IEnumerable<string> plannedKinds)`는 기존 alive 목록을 한 번 읽는다. 파괴됐거나 IsDead인 적은 제외하고 종류별 합과 총합을 같은 스냅샷에서 계산한다. 예정됐지만 현재 없는 종류는 0이고 실제 관측된 다른 종류도 포함한다. center와 유효 radius가 있을 때만 3차원 월드 거리로 반경 내 생존 적을 센다. 적용 반경은 스냅샷에 함께 남긴다. 전역 FindObjects나 게임 상태 변경은 없다. 위치가 없으면 nearbyAliveCount는 null이다.

사망 시 `OnPlayerDied`가 waves.Stop/ClearGroundWeapons보다 먼저 EndLogging을 호출한다. 값 복사 후 출력 순서는 다음과 같다.

`death_snapshot → 진행 중인 wave_summary(interrupted/death) → session_end → 저장소 Dispose → 기존 적/바닥 무기 정리 → 기존 GameOver 이벤트`

이미 상점 단계라 열린 웨이브가 없다면 사망 스냅샷과 세션 종료만 기록한다. 죽기 전 무기/적 조회를 GameOver 구독자에게 맡기지 않는다. death_snapshot payload는 player, enemies, lastDamage다. 반경은 초기화 때 유효한 LogData.deathEnemyRadius를 복사하며 현재 테이블 기본값은 10m다.

4차가 사용할 `LogDamageSnapshot`은 enemyTypeId/enemyWeaponId/attackPosition/actualDamage다. `Telemetry.SetLastDamage(snapshot)`은 값을 복사하므로 공격 적이 사라져도 보존된다. 실제 피해 이벤트 연결은 아직 없으며 현재 실제 플레이의 마지막 피해 출처는 unknown, 실제 피해량/공격 위치는 null이다. 4차는 치명 피해가 Died를 호출하기 전에 이 API를 호출해야 한다.

## 종료와 늦은 콜백

`End(reason, player, enemies, death)`는 세션당 한 번만 마감하고 마지막에는 1차 저장 서비스를 Dispose한다. session_end는 utc, playSeconds, reason, finalReachedWave, lastCompletedWave, totalKills를 가진다. 첫 웨이브 전 종료라면 두 웨이브 번호는 null이고, 관측한 처치가 없으면 totalKills는 실제 0이다. 상점에서 종료해도 이미 마감한 웨이브를 다시 중단으로 기록하지 않는다.

| 경로 | 이유와 처리 |
|---|---|
| OnPlayerDied | death; 정리 전 스냅샷과 열린 웨이브 중단 |
| PrepareForTitleReturn | return_to_title; 명시적 Title 이동 전에 호출 |
| GameOverPresenter의 Title 클릭 | 위 API 호출 후 기존 LoadScene. 이미 사망 종료했으면 추가 출력 없음 |
| OnApplicationQuit | application_quit; 관측한 애플리케이션 종료 콜백. 자발적인 사용자 종료라고 단정하지 않음 |
| OnDestroy만 관측 | unknown; 현재 조회 가능한 상태를 확보하고 마감 |
| OnDisable | 이 단계는 종료 처리하지 않음. 비활성화만으로 자진 종료를 추정하지 않음 |

현재 실제 Title 버튼은 게임 오버 화면에 있다. 향후 플레이 중 Title/재시작 경로를 추가하면 씬 변경 **전에** PrepareForTitleReturn 또는 End의 확인 가능한 사유를 사용해야 한다. 알려주지 않고 직접 씬을 파괴한 경우 OnDestroy/unknown이 최선이며 다른 오브젝트가 먼저 파괴됐다면 해당 플레이어/적 상태는 null일 수 있다. 강제 프로세스 종료에서 session_end는 보장되지 않는다.

진행 중인 슬롯 보상의 기존 실행 정책은 바꾸지 않았다. 후속 슬롯/발사체 수집기는 시작 당시 `Telemetry`/`Session`을 캡처해야 한다. 종료된 옛 Session의 TryRecord는 false이며 새 GameManager의 서비스로 다시 조회해 넘기면 안 된다. 종료 후 늦은 콜백을 위해 새 세션을 생성하지 않는다. 정상 웨이브 경계 뒤 결과는 1차의 originWaveNumber/originPhase 및 보정 계약을 사용한다.

## 후속 누적기 등록과 실패 격리

`ILogWaveSummaryCollector`는 Key, BeginWave(LogWaveBoundary), CloseWave(LogWaveBoundary)를 구현한다. `Telemetry.RegisterCollector(collector)`는 같은 키의 중복 등록, 진행 중 웨이브의 등록, 종료 후 등록을 거부한다. GameManager.Start 직후부터 첫 웨이브 코루틴이 재개되기 전까지 등록하거나, 향후 초기화 연결부에서 명시적으로 등록한다. 등록/마감 소유자는 메인 스레드다.

BeginWave는 웨이브별 초기화, CloseWave는 정상/중단의 최종 누적 구간 마감에 사용한다. LogWaveBoundary는 WaveNumber/StartedElapsedSeconds/ElapsedSeconds/Status/Reason을 제공한다. 수집기가 게임 상태를 변경하거나 다른 웨이브를 시작하는 데 사용하지 않는다. summaryId 예약은 생명주기가 소유하며 수집기가 별도로 TryCloseSummary를 호출하지 않는다.

summary의 summaries에는 기본 combat/ammo가 `{collectionStatus: "not_collected", data: null}`로 들어간다. 해당 키로 실제 수집기를 등록하면 collected와 실제 반환 데이터로 바뀐다. Begin/Close/결과 직렬화가 실패하면 해당 키만 failed/null과 진단을 남기고 전체 생명주기 출력은 계속된다. NaN/Infinity 검사를 공통 CopyPayload 경계에서도 수행해 잘못된 한 수집기 때문에 전체 wave_summary가 누락되지 않게 했다. 종료·중복 마감의 재진입을 방지한다.

파일 쓰기 실패는 기존 1차 정책을 따르고 로그 비활성화도 게임 처리를 바꾸지 않는다. Unity 상태 조회 경계의 예외는 ObserveLogging이 제한된 진단으로 격리한다. 스냅샷 한쪽의 조회가 실패해도 나머지 확보 가능한 값과 종료 처리를 시도한다. 상세 검증 근거는 `.omo/verification/log-phase2/RESULTS.md`에 있다.

## 사용자 Unity 확인 절차

AI는 아래 절차를 실행하지 않았다. 컴파일·순수 입력 검사와 실제 Unity 검증은 별개다.

1. Unity에서 새 파일 3개와 meta를 import한 뒤 컴파일 오류가 없는지 확인한다. Preload→Title에서는 Telemetry 세션 파일이 생기지 않아야 한다.
2. Title→Game 진입 후 실제 persistentDataPath/Telemetry에서 새 JSONL을 확인한다. session_start 1회, 첫 wave_start 1회이고 서로 같은 sessionId를 사용해야 한다. 시작 UTC·실제 fixedDeltaTime·맵 경로·빌드/데이터 지문을 확인한다.
3. 적을 일찍 전멸시킨 뒤 남은 시간 동안 플레이한다. enemies_cleared만 한 번 나오고 wave_summary는 제한 시간 완료 때까지 나오지 않아야 한다. 이번 단계는 틱별 위치/적 수 레코드를 만들지 않는다.
4. 웨이브 완료에서 실제 회복/보너스와 summary의 endPlayer/healthRestored/bonusPaid를 비교한다. 웨이브당 summary가 한 번이고 상점에서도 세션 시계가 이어져야 한다.
5. 다음 웨이브 도중 사망한다. death_snapshot의 양손 장전탄·예비탄·위치·생존 적 수·반경 값이 정리 전 상태와 맞는지 확인한다. death_snapshot→interrupted wave_summary→session_end 순서, 미지급 보상 null을 확인한다. 마지막 피해 출처는 현재 unknown이 정상이다.
6. 사망 후 Title로 돌아가도 session_end가 추가되지 않아야 한다. 다시 Game에 진입하면 새 sessionId, sequence 1, 경과 시간 초기값으로 시작해야 한다.
7. 첫 웨이브 전/웨이브 도중/상점에서 Play 종료 또는 애플리케이션 종료를 확인한다. 관측 경로에 따라 application_quit 또는 unknown이며 자진 종료를 임의 추정하지 않아야 한다. 첫 웨이브 전에는 가짜 웨이브 요약이 없어야 한다.
8. 회전 중 사망해 기존 슬롯 콜백이 나중에 실행되는 경우 새 세션으로 기록이 섞이지 않는지 확인한다. 슬롯 시작/결과 상세 레코드는 6차 구현 대상이며 이 단계에서는 기대하지 않는다.
9. 사용자 환경에서 LogData.enabled=false로 실행했을 때 게임 진행과 보상은 같고 새 분석 파일이 생기지 않는지 확인한 뒤 설정을 복원한다. 실제 디스크 실패·프레임 영향은 사용자 환경에서 별도 확인한다.

`Docs/로그-시스템-2차.synthetic.jsonl`은 순수 검사 입력으로 만든 합성 예시다. 실제 플레이 기록이 아니며 synthetic-* 무기/맵/탄종, 테스트 빌드 값과 주입한 UTC를 사용한다. 현재 실제 JSON 테이블의 게임 밸런스를 나타내지 않는다.
