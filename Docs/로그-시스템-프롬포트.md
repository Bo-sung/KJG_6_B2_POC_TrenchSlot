# 로그 시스템 작업 단계와 실행 프롬프트

작성일: 2026-10-30

## 목적과 사용 방법

`Docs/로그-시스템-기획안.md`를 실제 프로젝트에 연결하기 위한 **총 8차 작업**이다. 실제 Unity 프로젝트 경로는 `POC2/`이며, 아래 `Assets/`는 `POC2/Assets/`를 뜻한다. 각 차수의 프롬프트를 별도 AI 작업에 전달하고 순서대로 진행한다. 이 문서 작성은 구현 시작이나 완료를 뜻하지 않는다.

기반 계약 → 세션·웨이브 → FixedUpdate별 기록 → 전투 → 탄약 → 슬롯 → 상점 → 통합 검증 순서다. 기록 형식과 종료 순서를 먼저 정해 후속 수집기가 같은 세션·시계·저장 경로·요약 규칙을 사용하게 한다. PlayerWeapon·GameManager를 여러 차수가 수정하므로 무리하게 병렬 구현하지 않는다.

| 차수 | 범위 | 선행 작업 | 완료 기준 |
|---|---|---|---|
| 1차 | 설정·로그 계약·파일 저장 기반 | 기획·현재 코드 확인 | 공통 필드·null·시계·직렬화·저장 실패 정책과 검사용 메모리 저장소 준비 |
| 2차 | 세션·웨이브 생명주기·사망 스냅샷 | 1차 | 시작·완료·중단·종료를 한 번씩 기록하고 정리 전 상태 확보 |
| 3차 | FixedUpdate별 플레이어 위치·적 종류별 생존 수 | 2차 | 조작 가능한 매 FixedUpdate에 기록, 정지·조기 전멸·단계 전환 처리 |
| 4차 | 개별 사격·명중·처치·피해·장착 시간 | 2~3차 | 양손·산탄·실제 피해·피해 출처를 추적하고 웨이브별 전투 요약 생성 |
| 5차 | 탄약 수급·소비·부족 요약 | 4차 | 실제 변화량과 출처 집계, 재장전·바닥 무기 이동 중복 집계 방지 |
| 6차 | 슬롯 시작·결과·미완료 회전 | 5차 | 동일 회전 ID, 실제 심볼·지급량, 웨이브 경계를 넘는 결과 기록 |
| 7차 | 상점 제시·구매 성공·실패 | 6차 | 실제 진열·모든 구매 경로 기록, 중복 제시와 탄약 이중 집계 방지 |
| 8차 | 통합 검증·출력 예시·운영 문서 | 1~7차 | 실제 출력 구조·집계·종료·저장 실패 검증과 Unity 사용자 확인표 작성 |

## 현재 코드에서 확인한 연결 지점

아래는 작성 시점의 코드다. 각 작업 시작 시 최신 파일을 다시 확인한다. 과거 탄약 연결 작업의 단일 무기·고정 11상품 구조로 되돌리지 않는다.

| 영역 | 현재 파일·연결 지점 | 작업 시 주의점 |
|---|---|---|
| 게임 진행 | `Scripts/Game/GameManager.cs`: `StartWave`, `EndWave`, `OnPlayerDied`, `WaveStarted`, `WaveEnded`, `GameOver`, `EnemiesCleared` | 정상 EndWave는 적 정리→회복·보너스→WaveEnded 순서. 사망은 적·바닥 무기 정리 후 GameOver이므로 해당 이벤트만 받으면 사망 직전 적 수 등을 잃는다 |
| 적 상태 | `Scripts/Wave/WaveController.cs`: 살아 있는 목록, `AliveCount`, `EnemyKilled`, `Cleared`, `Stop` | Stop의 강제 제거는 처치가 아니다. 총 생존 수만으로 종류별 수나 사망 반경 내 적 수를 알 수 없다 |
| 플레이어 사격 | `Scripts/Player/PlayerWeapon.cs`: `Fired`, `HandFired`, `EnemyImpact`, `TryFire`, `TakeShot` | `Fired`에는 무기·손·실제 발사 위치가 없다. 기존 pelletGroup은 단발에서 0이므로 모든 사격의 고유 ID로 사용할 수 없다 |
| 무기 상태 | `Scripts/Model/WeaponInstance.cs`, `WeaponLoadout.cs`; PlayerWeapon의 `Current`, `Hand`, `HandAmmo` | 같은 종류 여러 자루, 휴대 슬롯, 아킴보, 파츠, 바닥 무기 이동이 존재한다. HUD용 양손 합계만 기록하면 손별 상태를 잃는다 |
| 피해·발사체 | `Scripts/Player/PlayerHealth.cs`, `Scripts/Projectile/Projectile.cs`, `Scripts/Enemy/Enemy.cs` | PlayerHealth의 기존 피해 정보에는 적 종류·무기 ID가 없다. 발사 당시 출처를 스냅샷으로 전달해야 적 사망·무기 교체 후에도 출처가 유지된다 |
| 탄약 | `Scripts/Model/AmmoInventory.cs`, `AmmoShop.cs`; PlayerWeapon의 재장전·`GrantSlotAmmo`; GameManager의 `TryCollectAmmo` 등 | Changed 이벤트에는 원인이 없다. 탄약 절감, 한 발씩 장전, 양손 보충, 팩 구매, 최대량 강화도 고려해야 한다 |
| 슬롯 | `Scripts/Slot/SlotMachinePresenter.cs`: `SpinStarted`, `SpinResolved`, `RollFaces`, `OnSpinStopped` | 기존 결과 이벤트에는 원본 3릴 배열이 없다. 시작 이벤트는 결제 후, 결과 이벤트는 지급 후 발생한다. 퍽·저금통 등 실제 배율 반영 필요 |
| 상점 | `Scripts/UI/ShopPresenter.cs`, `Scripts/Info/ShopInfo.cs`, GameManager의 `TryBuyWeapon/Part/Stat/Ammo/Heal/SlotUpgrade` | 현재는 개별 구매 API와 진열 갱신을 사용한다. 과거 `TryBuy(ShopData.Item)` 하나나 고정 상품 수를 전제로 구현하지 않는다 |
| 테이블 | `Scripts/Core/TableManager.cs`, `Scripts/Data/`, `Scripts/Info/`, `Resources/*.json` | 로그 설정도 같은 JSON→Data→Info→TableManager 경로 사용 |

## 공통 작업 규칙

1. 매 차수 시작 시 `Docs/작업지침.md`, `Docs/로그-시스템-기획안.md`, 이 문서와 앞선 진행 기록을 읽는다. 코딩 스타일은 Allman·파라미터 `_` 접두사 등 현행 지침을 따른다.
2. 로그는 실제 발생한 동작을 관찰한다. 사격 조건·적 AI·게임 보상·탄약 정책·상점 가격·입력·파츠·아킴보를 로그 수집 편의 때문에 바꾸지 않는다. 이번 로그 작업에 낮은 벽 사격 개선을 포함하지 않는다.
3. 관측용 이벤트 확장은 가능하되 기존 HUD·사운드·입력 등의 이벤트 구독과 호출 의미를 보존한다. 수집기 여러 개가 파일을 직접 쓰지 않고 1차의 공통 서비스로 전달한다. Unity 오브젝트 접근은 메인 스레드에서 값 복사 후 수행한다.
4. 새 파일의 `.meta`와 폴더 참조를 지킨다. UI를 추가할 필요는 없으며 씬 전체 재생성·BuildAll·열린 Unity 씬 덮어쓰기를 하지 않는다. 연결이 필요하면 기존 GameManager 또는 선택적 씬 저작 경로로 한정한다.
5. 기존 `use-orchestration` 조건을 유지한다. Unity Editor 실행·Play Mode·Unity 빌드·Unity API 실행 검증은 사용자가 한다. AI는 필요한 순수 C# 검사·Unity 외 C# 컴파일·정적 참조 검사를 수행하고 실제 Unity 검증과 구분한다. 워커를 사용할 경우 Qoder 최대 2명이며, 사용할 수 없다고 다른 종류로 대체하지 않는다.
6. 각 차수는 관련 검증과 변경 설명을 남긴다. 컴파일 성공을 실제 플레이 성공으로 표시하지 않는다. 커밋·푸시는 별도 요청 없이 하지 않는다.

## 후속 구현의 기본안과 경계 규칙

기획이 확정한 사항과 구현을 위해 제안하는 기본안을 구분한다. 아래 저장 방식·이벤트 이름·부족 집계 단위는 **이 문서의 구현 기본안**이며, 원 기획의 추가 확정 사항이라고 주장하지 않는다. 1차에서 채택한 실제 계약을 진행 기록에 남기고 이후 차수는 그 계약을 재사용한다.

- 저장 기본안: 네트워크 전송 없이 로컬 UTF-8 JSON Lines. `Application.persistentDataPath/Telemetry/<sessionId>.jsonl`에 한 줄 한 레코드로 기록한다. 일반 Debug 로그와 분석용 구조화 로그를 분리한다. 프로젝트 `POC2/Logs`는 Unity 내부 로그 위치이므로 분석 로그의 기본 저장 위치로 사용하지 않는다.
- 공통 봉투: `schemaVersion`, `eventType`, `sessionId`, `sequence`, `elapsedSeconds`, `waveNumber`, `phase`, `payload`. sequence는 세션 내 단조 증가한다. 웨이브 시작 전에는 waveNumber를 JSON null로 쓴다. 시작·종료 UTC는 ISO 8601로 기록한다. elapsedSeconds는 세션 활성 중 각 FixedUpdate에서 Unity의 `Time.fixedDeltaTime`을 한 번씩 더한 값으로 정한다. 상점에서도 세션 시간은 이어지고 이벤트는 발생 즉시 그 값을 읽는다. 한 틱 안에서 같은 시간이 찍힌 이벤트는 sequence로 구분한다. 로그 전용 시간 배율이나 별도 시간 누적 주기를 만들지 않는다.
- 알 수 없음은 실제 JSON null 또는 문자열 unknown. 실제 0과 구분한다. 프로젝트의 기존 JsonUtility만으로 nullable·사전 등 요구 형식이 충족되는지 확인해야 하며, 직렬화가 된다고 가정하지 않는다. 외부 패키지 추가가 필요하면 기존 의존성·승인 조건부터 확인한다.
- Fixed Delta Time 수집: 조작 가능한 매 FixedUpdate에 현재 시간·플레이어 위치(x, z)와 적 종류별 생존 수를 기록한다. 로그 설정에 별도 샘플 간격을 추가하지 않고 Unity의 실제 `Time.fixedDeltaTime`을 사용한다. 실제 적용값은 세션 시작에, 실행 중 바뀌면 변경 시각과 값을 기록한다. 로그 때문에 Unity 고정 시간 설정을 변경하지 않는다. 게임 시간 정지로 FixedUpdate가 실행되지 않으면 해당 수집과 경과 시간 누적도 멈춘다.
- 제안 수치: 사망 주변 적 반경 10m는 LogData.json의 조정 가능한 값으로 두고 실제 적용값을 사망 기록에 남긴다. flush 간격·버퍼 한도 등 추가 운영 수치도 채택 시 테이블화한다. 디스크 flush는 틱별 기록 생성과 별개이며, 버퍼링 때문에 중간 틱을 생략하거나 여러 틱을 하나로 합치지 않는다.
- 상태 스냅샷에는 활성 손·슬롯·무기 종류·무기 개체 식별자·손별 장전탄과 탄종별 공유 예비탄·최대량을 담는다. 무기 개체 ID는 세션 내에서 안정적이어야 하며 슬롯 교환·바닥 왕복 후에도 유지한다. 기록을 위해 게임 개체를 복제하지 않는다.
- 진행 중인 웨이브의 완료·중단 요약은 정확히 한 번 마감한다. 정상 종료는 실제 회복·보너스 지급 후 상태와 실제 지급량을 기록한다. 사망·나가기 중단은 완료 보상을 지급받은 것으로 기록하지 않는다. 정리 전 적·무기 상태와 마지막 피해는 먼저 값으로 확보한다.
- 상점 중 거래는 직전 웨이브의 이미 마감된 합계에 뒤늦게 더하지 않는다. 공통 phase와 거래 기록으로 보존하고 다음 웨이브 시작 상태에 반영한다. 웨이브를 넘는 슬롯·발사체에는 시작/발사 웨이브와 결과 발생 단계·웨이브를 구분해 남긴다. 늦은 결과로 요약을 수정해야 한다면 원본 덮어쓰기 대신 원본 키·개정 번호를 가진 보정 레코드와 해석 규칙을 사용하고, 마지막 개정만 합계에 적용한다.
- 개별 사격마다 단발·산탄 모두 유일한 shotId를 발급한다. 발사체 ID·spinId·구매 attemptId는 각각 다른 의미의 ID로 관리한다. 시각이 같아도 이벤트를 합치지 않는다.
- 발사 부족 기본안: 자동 연사 유지 입력은 빈 탄창 상태에 진입한 입력 구간당 1회, 버튼을 놓았다 다시 누르면 새 구간이다. 단발은 실제 입력 시도당 1회다. 재장전 부족은 명시적 재장전 입력 시도당 1회다. 쿨다운·입력 차단·사망·이미 재장전·다른 손 발사 가능 등은 빈 탄창 실패로 집계하지 않는다.
- 로그 쓰기 실패는 게임 진행·보상·구매를 중단시키지 않는다. 실패를 조용히 숨기지도 않으며, 제한된 경고와 진단 상태를 남긴다. 디스크 손실·강제 종료에서 모든 기록이 보장된다고 주장하지 않는다. session_end가 없으면 종료 미확인으로 해석한다.

## 1차 작업 프롬프트 — 설정·로그 계약·저장 기반

```text
TrenchSlot 로그 시스템 1차 작업을 수행해줘. 실제 Unity 프로젝트는 POC2/다.

Docs/작업지침.md, Docs/로그-시스템-기획안.md, Docs/로그-시스템-프롬포트.md의 공통 규칙·기본안을 읽어줘. 이번 범위는 설정·공통 계약·저장 기반이다. 도메인별 수집 연결은 후속 차수에서 한다.

1. 최신 코드와 Unity에서 사용 가능한 JSON 라이브러리를 확인하고, JSON Lines의 실제 null·배열·한국어·문자열 이스케이프·문화권 독립 숫자 형식을 지원하는 직렬화 방식을 정한다. 불필요한 외부 의존성을 추가하지 말고 채택 이유를 기록한다.
2. Assets/Resources/LogData.json, Scripts/Data/LogData.cs, Scripts/Info/LogInfo.cs를 만들고 TableManager에 등록한다. 활성 여부, schemaVersion, 사망 주변 적 반경(10m), 필요한 flush·버퍼 설정을 검증한다. 이동·적 수 수집 간격은 별도 설정으로 만들지 않고 매 FixedUpdate에 기록하도록 한다. Unity의 실제 Time.fixedDeltaTime을 읽고 로그를 위해 변경하지 않는다. 파일 경로는 persistentDataPath 아래로 제한하고 위험한 경로 조각을 그대로 결합하지 않는다.
3. Scripts/Logging/ 아래에 공통 레코드·페이로드 계약, 세션 서비스, 시계·출력 저장소 경계를 구성한다. 파일 저장소와 검사용 메모리 저장소를 제공한다. 순수 모델은 UnityEngine 없이 사용할 수 있게 하고 Unity 값은 어댑터에서 복사한다. 클래스 이름은 현행 코드에 맞추되 이후 단계가 사용할 실제 파일과 API를 기록한다.
```

틱별 기록 필드·시간 기준·정지/재개 정책:
- `player_position`: 공통 봉투 + fixedTick/player. player는 월드 x/z, 실제 조준 카메라의 월드 Euler yaw/pitch, 활성 손/슬롯, 손별 무기 종류/개체 ID/슬롯. 알 수 없는 카메라는 null이다.
- `enemy_alive_counts`: 공통 봉투 + 같은 fixedTick/enemies. enemies는 종류별 생존 수와 같은 목록에서 계산한 총합. 틱 경로는 반경 집계를 요청하지 않아 radius/nearbyAliveCount=null이다.
- 같은 실제 고정 틱의 두 레코드는 같은 elapsedSeconds·fixedTick과 별개의 sequence를 사용한다. 고정 틱 번호는 기존 시계가 실제 호출 때 하나씩 증가시킨 값이다.
- GameManager.FixedUpdate가 Time.fixedDeltaTime을 한 번 누적한 뒤 수집기는 같은 시간을 읽는다. 렌더 프레임·이동량·별도 간격 타이머·시간 배율로 생략/중복하지 않는다.
- InputGate·생존·이동 컴포넌트/CharacterController 활성·실제 Wave 단계·열린 웨이브·활성 세션/저장 상태를 확인한다. 정지 입력·슬롯 회전·조기 전멸은 수집을 막지 않는다. 상점은 시계만 누적하며 사망/세션 종료 뒤는 틱 기록을 멈춘다.
- FixedUpdate가 없는 정지 구간은 누적·수집·추정 보충이 없다. 재개 후 실제 실행 틱부터 이어간다. flush는 기록 횟수와 별개이며 기존 유한 버퍼를 사용한다.

적 종류별 집계 소유자·다음 API:
- WaveController가 LogEnemyPopulation을 보유한다. Begin은 양수 예정 종류로 초기화, 성공한 Spawn은 실제 KindId를 추가한다. 실제 등장 뒤 전멸한 비예정 종류도 같은 웨이브 안에서 0으로 보존한다.
- CaptureAliveSnapshot은 기존 alive의 null/IsDead를 제외하고 같은 스냅샷의 종류별 수·총합을 함께 계산한다. 전역 검색이나 별도 AliveCount 조회가 없다.
- Stop은 생존 목록을 비우되 종류 이력은 다음 Begin까지 유지한다. 다음 웨이브는 이전 예정/실제 종류를 초기화한다. 강제 제거는 기존대로 처치가 아니다. 2차 사망 정리 전 반경 스냅샷도 같은 API를 유지한다.
- `LogSession.FixedTick`, `LogFixedTickCollector.CanRecord/Record`, `LogPlayerTickSnapshot`, `LogHeldWeaponSnapshot`, `LogEnemyPopulation.Reset/ObserveKind/CreateSnapshot/AddAlive`. 상세 payload/각도 표현/실패 한계는 `Docs/로그-시스템-3차-계약.md` 참조.
