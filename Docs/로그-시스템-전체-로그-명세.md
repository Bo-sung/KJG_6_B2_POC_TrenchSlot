# 현재 로그 시스템 전체 명세 — 다른 AI 작업용

기준일: 2026-10-31. 현재 소스에서 확인한 **게임 분석 eventType 30종 전체**, 중첩 데이터, 저장 위치, 집계·수명 규칙과 별도 LogKit 출력을 기술한다. 앞으로 구현할 기획 항목이 아니라 현재 구현의 설명이다. 실제 Unity 실행 검증은 사용자가 담당한다.

## 1. 이 문서를 넘겨받은 AI가 먼저 알아야 할 것

- 실제 Unity 프로젝트는 `POC2/`다. 아래 소스 경로 `Scripts/...`는 `POC2/Assets/Scripts/...`를 뜻한다.
- 분석 writer는 `LogSession → FileLogStore` 하나다. 게임 사건을 별도 GameTelemetry/LogKit 집계에 다시 쓰지 않는다.
- 공통 필드 이름과 payload 필드 이름은 아래 철자를 그대로 사용한다. JSON 키는 camelCase이며 대소문자를 구분한다.
- 이 문서의 `int`, `long`, `number`는 각각 정수, 큰 정수, 실수 가능 수치다. JSON은 C# 자료형 정보를 따로 저장하지 않는다. `T?`는 JSON null 가능, `T[]`는 배열, `map<T>`는 문자열 키 사전이다. 중첩 스냅샷 자체도 수집하지 못했으면 null일 수 있다.
- null/unknown은 미확인이고 실제 0과 다르다. 다만 과거 호환 관측인 `slot_spin_requested/rejected`, `weapon_dropped/bought/picked_up`에는 빈 문자열·-1 등의 규칙이 남아 있다. 이 이벤트에 새 스냅샷 규칙을 일괄 적용하지 않는다.
- 분석 시 시간만으로 사건을 합치지 않는다. 순서는 sequence, 개별 사건 연결은 shotId/projectileId/spinId/attemptId/transactionId를 사용한다.
- wave_summary와 wave_summary_correction은 같은 사건의 전체 요약 개정본이다. 같은 summaryId에서는 최고 revision 하나만 채택한다.
- 슬롯/상점 결과에 복사된 탄약 목록은 원본 ammo_changed의 참조다. 합계에 다시 더하지 않는다.
- source와 실제 수집 지점을 확인한 뒤 수정한다. 로그 수집을 위해 보상·입력·물리·가격·피해 정책을 바꾸지 않는다. Unity Editor·Play Mode·Unity 빌드·Unity API 실행 검증은 직접 하지 않는다. 커밋·푸시는 별도 요청 대상이다.

## 2. 저장 위치와 설정

| 종류 | 경로·형식 | 소유자·설정 |
|---|---|---|
| 게임 분석 | `Application.persistentDataPath/Telemetry/<sessionId>.jsonl` | LogSession/FileLogStore, `Resources/LogData.json` |
| 콘솔·오류 | `Application.persistentDataPath/Logs/<LogKit sessionId>.jsonl` | LogKit, `Resources/TelemetryData.json` 및 선택적 TelemetryLocalData.json |
| Unity 자체 플레이어 로그 | 환경에 따라 `Player.log`, `Player-prev.log` 등 | Unity 엔진 자체 파일. 위 분석 JSONL의 스키마가 아님 |

현재 ProjectSettings의 companyName=DefaultCompany, productName=POC2다. 현재 Windows 사용자 환경에서 확인한 분석 폴더는 `C:\Users\JUNGLE\AppData\LocalLow\DefaultCompany\POC2\Telemetry\`다. 다른 PC/플랫폼의 경로는 실제 persistentDataPath를 따른다.

분석 파일은 한 판마다 새 GUID 이름을 사용하고 UTF-8 BOM 없이 한 줄 한 JSON으로 기록한다. 기존 파일을 덮어쓰지 않는다. Title 대기만으로 분석 세션을 만들지 않고 Game 모델 초기화 후 첫 웨이브 전에 시작한다. 분석 파일은 네트워크 전송하지 않으며 LogKit 자동 업로드 대상에도 포함하지 않는다.

현재 `LogData.json` 값:

```json
{
  "enabled": true,
  "schemaVersion": 1,
  "deathEnemyRadius": 10.0,
  "flushIntervalSeconds": 2.0,
  "maxBufferedRecords": 256,
  "maxBufferedBytes": 1048576,
  "maxRecordBytes": 65536,
  "maxWarningsPerSession": 3
}
```

flush 주기는 세션의 FixedUpdate 누적 시간 기준이며 벽시계 주기가 아니다. 용량 한계·명시적 Flush·종료도 flush를 유발한다. flush와 틱 기록 생성은 별개다. 별도 샘플 간격·로그 전용 시간 배율은 없다.

## 3. 모든 분석 이벤트의 공통 봉투

| 필드 | 형식 | 의미 |
|---|---|---|
| schemaVersion | int | 현재 설정값 1. 과거 개발 단계의 schemaVersion=1 파일이 현재 모든 payload와 같다고 단정하지 않는다 |
| eventType | string | 아래 30종 중 발생한 사건 |
| sessionId | string | 한 판의 GUID N 문자열, 하이픈 없는 32자리 |
| sequence | long | 세션 내 수락된 기록의 순번, 1부터 증가 |
| elapsedSeconds | number | 활성 세션에서 매 FixedUpdate의 실제 fixedDeltaTime을 한 번 더한 누적 게임 시간 |
| waveNumber | int? | 발생 당시 웨이브. 첫 웨이브 전에는 null |
| phase | string | 발생 단계. initializing, wave, shop, ended 및 어댑터의 game_over/unknown 등이 가능 |
| payload | object | 해당 사건 데이터. 서비스 자체는 null도 허용하지만 아래 정상 도메인 이벤트는 객체를 전달 |

상점에서도 시계는 진행한다. 게임 정지로 FixedUpdate가 없으면 시계와 틱 기록은 멈춘다. 한 틱 안의 여러 사건은 elapsedSeconds가 같을 수 있다. UTC와 elapsedSeconds를 혼용하지 않는다. waveNumber/phase는 사건 발생 당시 문맥이며 늦은 결과의 원래 소속은 별도 originWaveNumber/originPhase 또는 요약 plan.waveNumber를 본다.

합성 형식 예시(실제 플레이 기록 아님):

```json
{"schemaVersion":1,"eventType":"ammo_shortage","sessionId":"0123456789abcdef0123456789abcdef","sequence":12,"elapsedSeconds":0.2,"waveNumber":1,"phase":"wave","payload":{"ammoTypeId":"colt45","kind":"fire"}}
```

### ID 규칙

| ID | 형식·규칙 |
|---|---|
| 무기 개체 | `<sessionId>:weapon:<n>`; 같은 WeaponInstance 참조는 슬롯 교환·바닥 왕복 후에도 유지 |
| 사격 묶음 | `<sessionId>:shot:<n>`; 단발·산탄 모두 실제 사격마다 새 ID |
| 발사체 | `<sessionId>:projectile:<n>`; 각 생성 후보에 발급, player_shot.projectileIds에는 생성 성공분만 포함 |
| 회전 | `<sessionId>:spin:<n>`; 성공 회전의 수락된 시작에 연결 |
| 구매 시도 | `<sessionId>:purchaseattempt:<n>` |
| 탄약 사건/원인 그룹 | `<sessionId>:ammotransaction:<n>`; causeId가 같은 번호 공간의 그룹 ID인 경우도 있음 |
| 상점 제시 묶음 | `<sessionId>:offerset:<n>` |
| 상점 방문 | `<sessionId>:shopvisit:<n>`; 정비 시간 진입마다 새 ID, shop_opened~shop_closed 사이 상점 이벤트의 visitId |
| 상점 입력 | `<sessionId>:shopinput:<n>`; 상점 버튼 조작 한 번. 그 조작으로 생긴 이벤트가 interactionId로 참조 |
| 상점 무료 조작 | `<sessionId>:shopaction:<n>`; shop_equipment_result 한 건 |
| 요약 | `<sessionId>:wave:<waveNumber>`; revision=0 원본, 이후 개정 증가 |
| 파츠 개체 | `<sessionId>:part:<PartInstance.Uid>`; 공통 NewId enum과 별도로 구성 |
| 상품 | `<itemType>:<Uri.EscapeDataString(itemId)>`; 미지정 itemId는 null |
| 피격 대상 targetId | 현재 Projectile은 적의 Unity GetInstanceID를 문자열화. 테이블 ID나 다른 실행의 영구 ID가 아님 |

각 ID 공간의 카운터는 서로 독립이다. 기록 거부 등으로 ID 번호에 공백이 생길 수 있으므로 ID 번호 연속성을 완전성 조건으로 삼지 않는다. sequence가 연속이어도 수집하지 못한 사건까지 없었다는 뜻은 아니다.

## 4. 재사용되는 중첩 객체

이 절의 형식 이름은 설명용 이름이며 JSON에 type 필드나 클래스 이름을 추가하지 않는다. 스냅샷마다 키를 펼쳐 기록한다.

### Position3

`x:number?`, `y:number?`, `z:number?`: Unity 월드 좌표, 미터.

### HeldWeapon

`instanceId:string?`, `weaponTypeId:string?`, `hand:string?`, `slot:int?`.
현재 손에 든 무기 식별 정보. hand는 right/left, 슬롯 인덱스는 0부터 시작한다.

### PlayerTick

`x:number?`, `z:number?`, `yaw:number?`, `pitch:number?`, `activeHand:string?`, `activeSlot:int?`, `weapons:HeldWeapon[]?`.
위치는 월드 x/z, 카메라는 실제 Euler yaw/pitch 각도다. activeHand는 right/left/both 또는 null이 가능하다. 카메라를 얻지 못하면 방향은 null이다.

### WeaponSnapshot

| 필드 | 형식 | 의미 |
|---|---|---|
| instanceId | string? | 세션 내 무기 개체 ID |
| weaponTypeId | string? | WeaponData의 무기 종류 ID |
| ammoTypeId | string? | 탄종 ID |
| hand | string? | 현재 든 손, 들고 있지 않으면 null |
| slot | int? | 휴대 슬롯 인덱스 |
| active | bool? | 현재 손에 든 개체인지 |
| loadedAmmo | int? | 해당 무기 개체의 장전탄 |
| partIds | string[]? | 장착 파츠의 **종류 ID** 목록. 파츠 개체 ID 목록이 아님 |

### ReserveSnapshot

`ammoTypeId:string?`, `reserve:int?`, `maximum:int?`: 탄종별 공유 예비탄과 최대 보유량.

### PlayerSnapshot

`health:number?`, `money:int?`, `activeHand:string?`, `activeSlot:int?`, `position:Position3?`, `weapons:WeaponSnapshot[]?`, `reserves:ReserveSnapshot[]?`.
weapons에는 현재 손뿐 아니라 휴대 슬롯의 비활성 무기도 포함한다. 바닥 무기는 이 객체가 아니라 AmmoSnapshot에서 확인한다.

### EnemySnapshot

`aliveCount:int`, `aliveByKind:map<int>?`, `nearbyAliveCount:int?`, `radius:number?`.
aliveByKind는 적 종류 ID별 생존 수다. 현재 웨이브 예정 종류는 아직 스폰 전/전멸 후에도 0으로 유지하며 실제 관측한 추가 종류도 포함할 수 있다. 주변 수를 조회하지 않은 일반 틱에서는 nearbyAliveCount/radius가 null이다. 사망 조회는 적용 반경과 그 안의 생존 수를 포함한다.

### DamageSnapshot

`enemyTypeId:string`, `enemyWeaponId:string`, `attackPosition:Position3?`, `actualDamage:number?`.
출처 미확인은 unknown. attackPosition은 공격 출처의 위치이며 명중 지점과 구분한다. actualDamage는 플레이어 체력의 실제 감소량이다. 기본 사망 피해 객체는 출처 unknown, 위치/실제량 null일 수 있다.

### WavePlan

`waveNumber:int`, `durationSeconds:number`, `plannedEnemies:map<int>?`, `eraId:string?`, `enemyWeaponId:string?`.
해당 웨이브 제한 시간·예정 적 종류/수·시대·적 무기 정보다.

### AmmoWeaponSnapshot / AmmoSnapshot

- AmmoWeaponSnapshot: `instanceId:string?`, `weaponTypeId:string?`, `ammoTypeId:string?`, `location:string?`, `hand:string?`, `slot:int?`, `loadedAmmo:int?`.
- 실제 GameManager의 location은 carried 또는 floor다. floor 개체는 hand/slot이 null이다. 개체 없는 픽업의 loadedAmmo/instanceId는 null일 수 있다.
- AmmoSnapshot: `reserves:ReserveSnapshot[]?`, `weapons:AmmoWeaponSnapshot[]?`.
- weapons는 휴대 무기와 GroundRoot 아래 아직 소비되지 않은 바닥 픽업을 값 복사한다. 외부 월드 전체를 탐색하는 계약이 아니다.

### ShopProduct

`itemType:string?`, `itemId:string?`, `productId:string?`, `price:int?`, `targetSlot:int?`, `resolvedTargetSlot:int?`, `targetWeaponInstanceId:string?`, `offerIndex:int?`, `valid:bool`.

itemType은 Weapon/Part/Stat/Ammo/SlotUpgrade. itemId는 종류에 맞는 테이블 ID이며 price는 현재 ShopInfo 견적이다. valid는 데이터/상품 조회 유효성으로, 구매 가능이나 구매 성공을 뜻하지 않는다. targetSlot은 요청 슬롯, resolvedTargetSlot은 빈 슬롯 우선 등의 규칙을 반영한 예정 슬롯이다. targetWeaponInstanceId는 그 슬롯의 기존 무기 개체일 수 있다. offerIndex는 슬롯 업그레이드 진열 칸이다.

### ShopOffer / ShopOfferReference

- ShopOffer: `product:ShopProduct`, `placement:string`, `row:int`, `state:string`, `purchasable:bool`, `failureCode:string?`, `displayReason:string?`, `label:string?`, `priceText:string?`, `selected:bool`.
- placement: weapon_catalog, weapon_detail, weapon_buy, part_catalog, part_detail, part_buy, stat, ammo, upgrade.
- row는 배치 내 인덱스이며 상세 영역은 -1을 사용할 수 있다. selected는 현재 선택 상태다.
- label/priceText는 실제 UI 텍스트다. priceText는 숫자뿐 아니라 최대 표시·빈 문자열 등이 가능하다. displayReason도 현재 UI label 복사이므로 항상 독립적인 실패 설명 문장이라고 가정하지 않는다.
- state는 available 또는 locked/insufficient_funds/maximum_reserve/sold_out/already_purchased/purchase_limit/invalid_product/ui_disabled 등의 상태 코드다. 목록 선택 가능 여부와 유료 구매 가능 여부를 혼동하지 않는다. 최종 구매 판정은 실제 구매 결과를 사용한다.
- 품절 자리 표시의 productId는 null일 수 있다. null 상품을 실제 제시 상품으로 세지 않는다.
- ShopOfferReference: `offerSetId:string`, `revision:int`, `productId:string`, `placement:string`, `row:int`.

### ShopSnapshot

| 필드 | 형식·의미 |
|---|---|
| player | PlayerSnapshot? |
| maxHealth | number?; 최대 체력 |
| damageTakenMultiplier | number?; 받은 피해 배율 |
| moveSpeedMultiplier | number?; 이동 속도 배율 |
| reloadMultiplier | number?; 재장전 배율 |
| ammoCapacityBonus | int?; 최대 예비탄 추가량 |
| parts | `{instanceId:string?, partId:string?, attachedWeaponInstanceId:string?}[]?`; 보유 파츠 개체와 부착 대상 |
| stats | map<int>?; 스탯 ID별 구매 횟수 |
| perks | map<int>?; 퍽 ID별 스택 |
| upgrades | `{index:int, perkId:string?, bought:bool, soldOut:bool}[]?`; 슬롯 업그레이드 칸 상태 |

### SlotState / SlotOutcome

- SlotState: `waveNumber:int?`, `phase:string?`, `elapsedSeconds:number`, `player:PlayerSnapshot?`, `enemies:EnemySnapshot?`.
- SlotOutcome: `tripleFace:int`, `pairFace:int`, `multiplier:int`, `hasAmmo:bool`, `partCount:int`, `nextEraPartCount:int`, `isMiss:bool`, `isNearMiss:bool`.
- tripleFace/pairFace는 평가 결과의 face 인덱스이며 해당 조합이 없으면 현재 평가기가 -1을 쓴다. 원본 3릴은 별도 faces/symbolIds다. multiplier는 현금 결과 배수이고 partCount/nextEraPartCount는 결과의 파츠 수 정보다.

| 42 | shop_scroll_changed | Logging/LogShopCollector.ObserveScroll |

아래 각 절은 **payload 내부 필드 전체**를 나열한다. 공통 봉투 8개 필드는 별도다.

### 5.1 session_start

발생: GameManager.InitializeLogging에서 Game 모델 초기화 후, 첫 BeginWave 전 한 번.

`utc:string`, `buildVersion:string?`, `buildGuid:string?`, `dataVersion:string?`, `dataFingerprint:string?`, `mapId:string?`, `fixedDeltaTime:number?`.

utc는 시작 UTC ISO 8601이다. buildVersion/buildGuid는 Unity Application 값, mapId는 현재 Game 씬 경로다. 현재 dataVersion은 명시적으로 null이고, dataFingerprint는 로드된 관련 테이블 값의 SHA-256 지문이다. 빌드/데이터 버전을 모르면 꾸며내지 않는다.

### 5.2 session_end

발생: 사망, 명시적 Title 복귀, 애플리케이션 종료, OnDestroy 등의 종료 경계. 중복 마감 방어가 있다.

`utc:string`, `playSeconds:number`, `reason:string`, `finalReachedWave:int?`, `lastCompletedWave:int?`, `totalKills:int`.

reason의 현재 게임 호출 값은 death/return_to_title/application_quit/unknown이다. 생명주기 API는 다른 명시적 사유도 받을 수 있다. finalReachedWave와 lastCompletedWave를 구분한다. 첫 웨이브 전 종료면 둘 다 null일 수 있다. playSeconds는 누적 게임 시간이다. 종료 후 추가 분석 기록은 거부한다.

### 5.3 wave_start

발생: GameManager.StartWave가 실제 웨이브를 시작한 뒤 BeginWave.

`plan:WavePlan`, `player:PlayerSnapshot?`.

시작 시점 자원·무기·장전탄·예비탄을 보관한다. 현재 웨이브의 전투·탄약 수집기도 이 경계에서 초기화한다.

### 5.4 enemies_cleared

발생: 열린 웨이브의 적 전멸을 처음 관측했을 때. 이것만으로 웨이브 완료가 아니다.

`clearedElapsedSeconds:number`, `waveElapsedSeconds:number`, `kills:int`.

전멸한 세션 시각·웨이브 시작 이후 시간·그때까지 처치 수다. 플레이어가 조작 가능하면 전멸 후에도 틱 기록을 계속한다.

### 5.5 wave_summary

발생: 정상 제한 시간 종료는 실제 회복·보너스 반영 후, 사망/나가기는 정리 전 중단 마감. 웨이브별 논리 마감은 한 번이다.

| 필드 | 형식·의미 |
|---|---|
| summaryId / revision | string / int; 동일 웨이브 요약 키와 원본 0 |
| status / reason | string / string?; completed/time_limit 또는 interrupted/종료 사유 |
| startedElapsedSeconds / endedElapsedSeconds / waveElapsedSeconds | number; 세션 시작/끝 시각과 웨이브 경과 시간 |
| plan | WavePlan |
| startPlayer / endPlayer | PlayerSnapshot?; 시작/마감 상태 |
| enemiesBeforeCleanup | EnemySnapshot?; 정리 전 적 상태 |
| kills | int; 생명주기가 관측한 웨이브 처치 수 |
| clearedElapsedSeconds / clearDurationSeconds | number?; 전멸 세션 시각과 전멸까지 걸린 시간, 없으면 null |
| rewardsApplied | bool; 정상 완료 보상 적용 여부 |
| bonusPaid / healthRestored | int? / number?; 실제 보너스·회복. 중단 시 null |
| summaries | `{combat:SummarySection, ammo:SummarySection}`; 각 수집기 결과 |

SummarySection은 `{collectionStatus:string, data:object?}`다. collectionStatus는 collected/not_collected/failed. 실패·미수집을 0으로 취급하지 않는다.

**combat.data 전체 구조**:

- `weapons:WeaponCombatTotals[]`: 개체별.
- `weaponTypes:WeaponCombatTotals[]`: 종류별. 이 집계의 instanceId는 null이다.
- `damageReceived:{enemyTypeId:string, actualDamage:number, hits:int}[]`: 적 종류별 실제 받은 피해와 피해 사건 수.
- WeaponCombatTotals: `instanceId:string?`, `weaponTypeId:string?`, `equippedSeconds:number`, `shots:int`, `requestedProjectiles:int`, `projectiles:int`, `hitProjectiles:int`, `hitShots:int`, `kills:int`, `actualDamageDealt:number`.
- shots는 성공 사격 묶음, requestedProjectiles는 생성 요청 수, projectiles는 실제 생성 수다. hitShots는 적 하나 이상에 명중한 사격 묶음, hitProjectiles는 적중 탄 수다. 산탄 한 묶음이 여러 적에 맞아도 hitShots는 1이다.
- kills는 수집기 내 targetId 중복을 제거한 처치다. wave_summary.kills/session_end.totalKills와 수집 경로가 다르므로 외부 원인 처치까지 반드시 같다고 가정하지 않는다.
- 장착 시간은 장착 변경·웨이브 마감 때 열린 구간을 누적한다. 양손 두 무기의 합계는 벽시계 웨이브 길이보다 클 수 있다.

**ammo.data 전체 구조**:

- `start:AmmoSnapshot?`, `end:AmmoSnapshot?`, `ammoTypes:AmmoTotals[]`.
- AmmoTotals: `ammoTypeId:string`, `consumed:long`, `discarded:long`, `reloaded:long`, `moved:long`, `emptyFireAttempts:int`, `emptyReloadAttempts:int`, `acquiredBySource:map<long>`.
- reloaded는 내부 이동량이며 consumed/acquired에 더하지 않는다. moved는 바닥 이동 관측량이므로 경제 획득량이 아니다. acquiredBySource는 실제 수락된 수량이다.

### 5.6 wave_summary_correction

발생: 마감된 웨이브에서 발사한 탄의 늦은 적 명중이 아직 활성인 같은 세션에 도착할 때.

payload는 **wave_summary와 동일한 전체 구조**다. 같은 summaryId, 증가한 revision, 갱신된 summaries.combat와 보존된 다른 필드를 포함한다. 차이만 담은 patch가 아니다. 봉투 waveNumber/phase는 결과 발생 현재 시점일 수 있다. 소속은 payload.plan.waveNumber로 찾는다. 최고 revision만 적용한다. 세션 종료 후 새 세션을 보정하지 않는다.

### 5.7 wave_intermission_started

발생: GameManager.EndWave가 Shop 단계로 전환한 뒤.

`intermissionSeconds:number`, `balance:int`: 정비 시간과 당시 소지금. 매 프레임 남은 시간을 기록하는 이벤트가 아니다.

### 5.8 fixed_delta_time_changed

발생: 실제 FixedUpdate에 전달된 fixedDeltaTime이 직전 적용값과 다를 때.

`previousFixedDeltaTime:number`, `fixedDeltaTime:number`.

해당 틱은 새 값으로 누적된다. 수집기가 Time 설정을 바꾸는 이벤트가 아니다.

### 5.9 player_position

발생: 열린 wave·생존·이동 조작 가능 조건을 만족하는 매 FixedUpdate에 한 번.

`fixedTick:long`, `player:PlayerTick?`.

fixedTick은 세션의 전체 실제 FixedUpdate 카운터이므로 상점 틱 등을 지나면 위치 기록 사이에 번호 공백이 있을 수 있다. 위치가 같아도 생략하지 않는다. 한 렌더 프레임 안에 여러 FixedUpdate가 있으면 각각 기록한다.

### 5.10 enemy_alive_counts

발생: player_position과 같은 수집 호출의 바로 다음 기록.

`fixedTick:long`, `enemies:EnemySnapshot?`.

같은 fixedTick·elapsedSeconds의 player_position과 짝을 이룬다. 실패/크기 제한으로 한쪽이 빠진 파일은 완전한 짝이라고 추정하지 않는다.

### 5.11 weapon_equipped

발생: 실제 손에 든 무기 집합이 이전 관측과 달라졌을 때. GameManager.SynchronizeCombatEquipment가 공급한다.

`weapons:HeldWeapon[]`.

같은 장착 상태 반복은 기록하지 않는다. 빈 배열은 장착 집합이 비었음을 뜻할 수 있다. 초기 장착도 session_start 뒤에 나올 수 있다.

### 5.12 player_shot

발생: PlayerWeapon.TryFire의 실제 성공 사격에 대해 발사체 생성 시도를 마친 뒤 FinalizeShot.

`shotId:string`, `weaponInstanceId:string?`, `weaponTypeId:string`, `hand:string`, `magazineAmmo:int?`, `reserveAmmo:int?`, `akimbo:bool?`, `aiming:bool?`, `origin:Position3`, `originWaveNumber:int?`, `originPhase:string`, `firedElapsedSeconds:number`, `requestedProjectileCount:int`, `createdProjectileCount:int`, `failedProjectileCount:int`, `projectileIds:string[]`.

origin은 실제 ProjectileSpawner.Launch에 사용하는 위치다. 총구가 막히면 카메라 위치를 쓰는 기존 경로를 반영한다. magazineAmmo/reserveAmmo는 현재 호출부가 사격 후 공개 Ammo/ReserveAmmo 속성에서 캡처한 값이다. Ammo는 아킴보일 때 양손 장전탄 합계다. **magazineAmmo를 손별 발사 전 장전탄으로 단정하지 않는다.** 정확한 손별 소비는 같은 shotId의 ammo_changed.loadedDelta/consumed를 본다.

shotId는 산탄이어도 하나다. projectileIds는 생성 성공분만 포함하며 생성 실패한 후보 ID는 이 배열에 없다. ammo_changed가 player_shot보다 먼저 sequence에 나타날 수 있으므로 참조 검사는 파일 전체 또는 지연 해석으로 처리한다.

### 5.13 projectile_impact

발생: 플레이어 발사체가 실제 충돌 결과를 Resolve하고 원래 LogShotContext에 전달할 때. 같은 발사체의 중복 결과는 제거한다.

`shotId:string`, `weaponInstanceId:string?`, `weaponTypeId:string`, `hand:string`, `originWaveNumber:int?`, `originPhase:string`, `impact:CombatImpact`, `lateResult:bool`.

CombatImpact 전체: `projectileId:string`, `hitEnemy:bool`, `killed:bool`, `headshot:bool`, `helmetHit:bool`, `staggered:bool`, `targetId:string?`, `enemyTypeId:string?`, `actualDamage:number`, `point:Position3?`.

point는 충돌 지점이다. 적 외 벽/지면 충돌도 hitEnemy=false로 남을 수 있고 targetId/enemyTypeId는 null일 수 있다. actualDamage는 적 체력의 실제 감소량으로 과잉 피해를 제한한다. 피해 0인 접촉을 양수 피해로 바꾸지 않는다. lateResult는 발사 원래 웨이브가 이미 마감됐는지다. 사거리/수명 만료의 빗나감은 별도 impact/종료 이벤트를 만들지 않는다.

### 5.14 player_damage

발생: PlayerHealth가 체력 감소를 적용한 뒤, 사망 이벤트보다 먼저 PlayerDamaged.

payload는 DamageSnapshot 전체다: `enemyTypeId`, `enemyWeaponId`, `attackPosition`, `actualDamage`.

실제 감소가 양수일 때 기록한다. 요청 피해나 방어 적용 전 수치가 아니다. 공격 출처를 발사 시점에 값 복사하므로 적 오브젝트가 파괴돼도 출처를 유지한다. 회복은 이 이벤트가 아니다.

### 5.15 death_snapshot

발생: GameManager.OnPlayerDied가 waves.Stop/ClearGroundWeapons를 하기 전에 EndLogging(death).

`player:PlayerSnapshot?`, `enemies:EnemySnapshot?`, `lastDamage:DamageSnapshot`.

주변 반경은 실제 적용된 LogData.deathEnemyRadius를 enemies.radius에 기록한다. 마지막 피해를 모르면 unknown/null 기본 객체다. 사망 정리 후 적 수 0을 사망 직전 상태처럼 기록하지 않는다.

### 5.16 ammo_changed

발생: AmmoInventory·PlayerWeapon·GameManager의 실제 탄약 변경/이동 관측. 웨이브 밖 같은 활성 세션에도 개별 사건은 기록한다.

| 필드 | 형식·의미 |
|---|---|
| transactionId | string; 이 탄약 사건 고유 ID |
| causeId | string?; shotId/spinId/attemptId 또는 관련 변경 그룹 ID |
| source | string; 아래 출처 |
| ammoTypeId | string; 미확인 시 unknown |
| weaponInstanceId / hand / shotId | string?; 관련 무기·손·사격 |
| reserveDelta / loadedDelta | int; 예비탄/장전탄 실제 증감, 감소는 음수 |
| acquired / consumed / discarded | int; 신규 획득/발사 소비/폐기량 |
| transferred / moved | int; 재장전 내부 이동/바닥 이동 관측량 |
| reserveMaximumBefore / reserveMaximumAfter | int?; 최대량 변경 시 전후 상한 |

현재 source와 의미:

| source | 의미 |
|---|---|
| initial_weapon | 초기 무기의 장전탄. 첫 웨이브 시작 전 기준량에 반영 |
| new_weapon | 구매로 새로 생성한 무기의 장전탄 |
| world_weapon | 개체 없는 월드 픽업에서 새 무기 개체가 생성됐을 때 장전탄 |
| drop | 탄약 드롭 픽업의 상한 내 실제 수급 |
| shop_pack | 상점 팩으로 실제 늘어난 예비탄 |
| slot_reserve | 슬롯으로 실제 늘어난 예비탄 |
| slot_loaded | 슬롯 직접 보충 API로 실제 늘어난 손별 장전탄. 현재 보상 연결에서 호출하는지와 별개로 구현된 관측 경로 |
| shot | 발사 전후 해당 손 장전탄 감소. 탄 절감이면 소비 0 |
| reload | 예비탄 -n, 장전탄 +n의 이동 |
| weapon_drop / weapon_pickup | 같은 개체의 바닥 이동. 신규 획득이 아님 |
| capacity_return | 탄창 축소분 중 예비탄으로 실제 반환된 양. acquired=0 |
| capacity_shrink | 탄창에서 실제 제거한 양과 반환하지 못한 폐기량 |
| maximum_changed | 최대 예비탄 전후 및 초과분 실제 폐기 |
| unknown | 출처를 지정하지 않은 추가 경로. 현재 Add 기본값 |

0발 지급도 결과를 관측했으면 기록할 수 있다. reserveDelta/loadedDelta는 상태 변화, acquired/consumed/discarded는 경제 분류이므로 서로 모두 합산하지 않는다. capacity_return과 capacity_shrink는 같은 causeId로 연결될 수 있다. 원본 사건의 출처별 수량을 정가·명목 지급량으로 대체하지 않는다.

### 5.17 ammo_shortage

발생: 열린 웨이브에서 실제 자격 있는 빈 탄창 발사/예비탄 없는 명시적 재장전 시도.

`ammoTypeId:string`, `kind:string`(fire 또는 reload).

자동 발사는 한 유지 입력 구간의 첫 빈 탄창 실패 1회, 단발은 시도당 1회다. 버튼 해제/입력 차단은 유지 구간을 닫는다. 쿨다운·사망·차단·이미 재장전·다른 손 발사 가능 등은 부족으로 세지 않는다.

### 5.18 slot_spin_requested

발생: SlotMachinePresenter가 실제 결제/시작을 시도하는 경로에 진입했을 때. 모든 거부 입력에 반드시 선행하는 이벤트는 아니다.

`cost:int`, `balance:int`, `reason:string`(현재 빈 문자열).

이 이벤트에는 spinId가 없다. 비용·잔액은 요청 당시 값이다. 요청 이벤트를 성공 회전으로 세지 않는다.

### 5.19 slot_spin_rejected

발생: 상호작용 조건 불충족, 결제 실패, 릴 시작 실패 등.

`cost:int`, `balance:int`, `reason:string`.

현재 reason은 Spinning/NotReady/WaveInactive/InsufficientFunds/ReelsBusy다. 릴 시작 실패는 환불 후 잔액을 기록한다. 일부 미준비 경로는 잔액을 얻지 못하면 기존 호환 방식으로 0을 전달할 수 있다. spinId가 없고 성공 회전과 1:1 대응하지 않는다.

### 5.20 slot_spin_started

발생: BeginSpin 성공 뒤, 결제 전 스냅샷과 원본 RollFaces를 전달. 시작 레코드가 수락된 경우에만 진행 문맥을 등록한다.

`spinId:string`, `originWaveNumber:int?`, `originPhase:string?`, `startedElapsedSeconds:number`, `actualCost:int`, `baseCost:int`, `spinSeconds:number`, `faces:int[3]`, `symbolIds:string?[3]`, `before:SlotState`.

before는 결제 전 상태다. actualCost는 할인 반영 실제 비용, baseCost는 기본 회전 비용/지급 계산 기준이다. faces는 릴 인덱스 순서의 실제 결과이고 symbolIds는 해당 원본 심볼 ID다. 지급 결과에서 재추첨·역산하지 않는다.

### 5.21 slot_spin_healed

발생: 성공 회전 직후 실제 회복을 적용한 뒤. 같은 spinId에 한 번.

`spinId:string`, `actualHealthRestored:number`, `healthAfter:number?`.

실제 회복 0도 기록할 수 있다. 별도 SpinHealed 게임 이벤트는 회복 양수일 때만 발생하므로 그 이벤트 수와 반드시 같지는 않다.

### 5.22 slot_spin_resolved

발생: 실제 슬롯 보상 지급 전후 값을 캡처한 뒤. 원래 spinId당 한 번.

`spinId:string`, `originWaveNumber:int?`, `originPhase:string?`, `startedElapsedSeconds:number`, `resolvedElapsedSeconds:number`, `faces:int[3]`, `symbolIds:string?[3]`, `outcome:SlotOutcome`, `piggyMultiplier:number`, `cashBonusMultiplier:number?`, `calculatedPayout:int`, `plannedPartIds:string[]?`, `actualMoneyDelta:long?`, `balanceAfter:int?`, `ammoGranted:AmmoChange[]`, `before:SlotState?`, `after:SlotState?`.

AmmoChange는 ammo_changed payload와 동일한 전체 객체 복사다. causeId=spinId, transactionId로 원본을 찾는다. before/after는 **지급 전후**이며 시작 이벤트의 결제 전 before와 다르다. actualMoneyDelta=지급 후 잔액-지급 전 잔액이다. calculatedPayout은 현재 호출부의 현금 당첨 계산분으로, 다른 보상 적용까지 포함한 실제 순증과 항상 같다고 가정하지 않는다. cashBonusMultiplier는 현금 당첨 계산이 없으면 null일 수 있다.

plannedPartIds는 계획된 파츠 **종류 ID**다. 실제 생성 개체의 ID/성공 증거로 쓰지 않는다. 이미 닫힌 웨이브 이후 지급이라면 현재 phase/wave와 origin을 구분한다. 한 관측 구간에 외부 재진입 잔액 변화가 있으면 실제 순증에도 포함될 수 있다.

### 5.23 slot_spin_incomplete

발생: 세션 종료 때 pending 회전, 지급 중단, 결과 수집 실패 등으로 정상 결과를 확정 기록하지 못했을 때.

`spinId:string`, `originWaveNumber:int?`, `originPhase:string?`, `startedElapsedSeconds:number`, `status:string`(incomplete), `reason:string?`.

현재 명시적 사유에는 payout_interrupted/result_collection_failed 및 세션 종료 사유가 있다. outcome/실제 지급량은 넣지 않는다. incomplete는 보상 0 확정이 아니다. 저장 실패는 이 종료 행 자체도 유실시킬 수 있다.

### 5.24 shop_offers_presented

발생: ShopPresenter.Logging.LateUpdate 또는 구매 참조 획득 직전 실제 표시 상태를 읽어, 상점이 열려 있고 내용이 이전과 달라졌을 때.

`offerSetId:string`, `revision:int`, `presentation:{balance:int?, selectedWeaponId:string?, selectedPartId:string?, offers:ShopOffer[], inventory:ShopInventory?}`, `visitId:string?`.

ShopInventory = `{activeHand:string?, activeSlot:int?, weapons:WeaponSnapshot[]?, reserves:ReserveSnapshot[]?, parts:{instanceId, partId, attachedWeaponInstanceId}[]}` — 화면의 유저 정보·보관함과 같은 시점의 휴대 무기·예비탄·파츠 개체다. 실제 게임에서는 항상 들어가며, 보관·장착·예비탄 변화도 revision을 올린다. inventory 키가 없는 행은 이전 버전 기록이다.

상점 열기(화면 표시)마다 새 offerSetId와 revision=0. 같은 내용 반복 Refresh는 생략한다. 잔액·가격·선택·노출 행·상태·보유품 변화는 개정한다. 닫기는 내부 제시 상태를 지운다. 방문 종료는 shop_closed, 화면 숨김은 shop_view_hidden으로 따로 남는다. 노출은 활성·투명도·면적·마스크/스크롤 viewport/캔버스 사각 교차로 판정한다. 실제 시선·다른 창에 의한 가림까지 보장하지 않는다. 무료 장착/분리/휴대 슬롯/아킴보 버튼은 유료 상품 제시에서 제외한다.

### 5.25 shop_purchase_attempt

발생: 현행 TryBuyWeapon/Part/Stat/Ammo/SlotUpgrade 공통 RunLoggedPurchase가 구매 함수를 호출하기 전.

`attemptId:string`, `product:ShopProduct`, `offer:ShopOfferReference?`, `before:ShopSnapshot?`, `visitId:string?`, `interactionId:string?`.

interactionId는 이 시도를 일으킨 shop_ui_input이며, 직접 API 호출(검사 코드 등)은 null이다. UI가 넘긴 참조가 현재 set/revision/product/placement/row/대상과 맞을 때만 offer를 연결한다. 직접 API·오래된 참조·노출되지 않은 대상은 null이다. 상점 밖 호출도 활성 세션이면 발생 phase에 시도를 기록한다. 세션 밖이나 기록 비활성/실패 상태는 시도가 기록되지 않을 수 있다.

### 5.26 shop_purchase_result

발생: 같은 공통 경계의 finally에서 정상 반환/모든 조기 거부/예외를 관측한 뒤. 원래 예외는 게임 호출자에게 계속 전파된다.

`attemptId:string`, `product:ShopProduct`, `offer:ShopOfferReference?`, `success:bool`, `failureCode:string?`, `displayReason:string?`, `before:ShopSnapshot?`, `after:ShopSnapshot?`, `actualSpent:long?`, `actualHealthRestored:number?`, `createdWeaponIds:string[]?`, `createdPartIds:string[]?`, `ammoChanges:AmmoChange[]`.

success는 구매 함수가 반환했고 실패 문자열이 비었을 때다. 성공 코드=null. 예외는 failureCode=exception이며 displayReason은 예외 본문을 자동 저장하는 필드가 아니다. actualSpent=전 잔액-후 잔액이고 음수 가능성을 임의로 막지 않는다. 실패의 실제 지출 0과 스냅샷 미확인의 null을 구분한다. actualHealthRestored는 양수 체력 차이이며 상품 종류가 회복이라는 뜻은 아니다.

createdWeaponIds/createdPartIds는 관측 전후 ID 집합의 새 항목이다. 스냅샷 미확인이면 null일 수 있다. ammoChanges는 causeId=attemptId인 canonical ammo_changed의 전체 복사다. 이것을 획득 합계에 다시 더하지 않는다. stats/perks/upgrades와 배율의 실제 적용 상태는 after에서 확인한다.

실패 코드 전체:

| 코드 | 의미 |
|---|---|
| shop_closed | 정비 시간 밖 |
| insufficient_funds | 자금 부족 |
| invalid_product | 무효 상품/테이블 ID |
| locked | 아직 해금되지 않은 상품 |
| invalid_target_slot | 무효 교체 슬롯 |
| invalid_offer_index | 무효 슬롯 업그레이드 칸 인덱스 |
| sold_out | 품절 |
| already_purchased | 해당 진열에서 이미 구매 |
| purchase_limit | 퍽 등의 구매/스택 한도 |
| maximum_reserve | 예비탄 최대 |
| no_effect | 보충/적용할 변화 없음 |
| missing_pickup_prefab | 교체용 픽업 프리팹 없음 |
| no_drop_space | 교체 무기를 놓을 공간 없음 |
| purchase_in_progress | 탄약 구매 재진입 처리 중 |
| exception | 구매 함수 예외 |
| unknown | 기존 문구를 분류하지 못함 |

shop_equipment_result만 쓰는 코드: part_not_owned(보유하지 않은 파츠), incompatible_weapon(다른 무기용 파츠), attached_to_ground_weapon(바닥 무기에 붙은 개체), already_attached(대상에 이미 장착), ammo_overflow(줄어든 탄창의 장전탄을 예비탄에 돌려줄 수 없음), part_not_attached(분리할 장착 개체 없음), akimbo_not_pistol, akimbo_needs_pair. shop_closed·exception·unknown은 공통이다.

ui_disabled는 상품 제시 상태에서 쓰며 현재 구매 실패 분류기의 일반 반환 코드는 아니다. 현재 유료 Heal 상품/API는 없고 체력 회복은 슬롯 정책이다. Stat의 maxHealth 구매는 존재한다. 구매 시도 없이 지나간 이유를 추정하지 않는다.

### 5.27 shop_purchase_incomplete

발생: 세션 종료 중 pending 구매 또는 결과 스냅샷/레코드 수집 실패.

`attemptId:string`, `reason:string?`.

현재 reason은 result_collection_failed 또는 세션 종료 사유다. 성공/실패나 실제 지급량을 추측하지 않는다.

### 5.28 weapon_dropped

발생: GameManager에서 구매 교체 또는 픽업 교환으로 기존 무기를 바닥에 놓은 뒤.

`weaponId:string`, `slot:int`, `replacedWeaponId:string`, `magazine:int`, `reason:string`.

여기서 weaponId는 무기 **종류 ID**다. 이 호환 관측에는 무기 개체 ID가 없다. dropped의 slot=-1, replacedWeaponId는 빈 문자열이다. 현재 reason은 Bought/PickupSwap이다. 별도 ammo_changed(source=weapon_drop)가 장전탄 이동을 관측하므로 추가 획득으로 합산하지 않는다.

### 5.29 weapon_bought

발생: GameManager의 실제 무기 생성/슬롯 배치 성공 뒤.

`weaponId:string`, `slot:int`, `replacedWeaponId:string`, `magazine:int`, `reason:string`.

구매한 종류 ID, 들어간 슬롯, 바닥으로 교체된 무기의 종류 ID(없으면 빈 문자열), 신규 무기의 장전탄이다. reason은 현재 빈 문자열. attemptId 없는 보조 관측이므로 구매 시도/성공의 기준은 shop_purchase_attempt/result다. 두 이벤트를 별도 구매 두 번으로 세지 않는다.

### 5.30 weapon_picked_up

발생: GameManager가 바닥 픽업을 교환/빈 슬롯 배치에 성공한 뒤.

`weaponId:string`, `slot:int`, `replacedWeaponId:string`, `magazine:int`, `reason:string`.

픽업한 종류 ID·슬롯·교환된 종류 ID·장전탄을 기록한다. reason은 현재 빈 문자열. 개체가 유지된 픽업인지 신규 생성인지는 이 종류 기반 이벤트만으로 판단하지 말고 무기 개체 스냅샷과 ammo_changed의 world_weapon/weapon_pickup을 함께 본다.

### 5.31 shop_opened

발생: GameManager.SetPhase가 Shop으로 바뀐 직후(웨이브 종료). 화면 표시보다 먼저다.

`visitId:string`, `nextWaveNumber:int?`, `intermissionSeconds:number?`(남은 정비 시간), `durationSeconds:number?`(정비 시간 설정), `utc:string`, `state:ShopSnapshot?`(진입 시 상태).

### 5.32 shop_closed

발생: Shop 단계를 벗어나기 직전(봉투 phase는 아직 shop), 또는 세션이 상점 안에서 끝날 때. 방문마다 정확히 한 번.

`visitId:string`, `reason:string`, `detail:string?`, `nextPhase:string?`, `interactionId:string?`, `intermissionLeft:number?`, `dwellSeconds:number?`(진입 후 고정 시계 경과), `utc:string`, `state:ShopSnapshot?`(퇴장 시 상태).

| reason | 의미 |
|---|---|
| skip | StartNextWave() 호출. UI 다음 웨이브 버튼이면 interactionId가 그 입력, 직접 호출이면 null |
| timeout | 정비 시간이 0이 되어 자동 시작. interactionId=null |
| phase_changed | 그 밖의 단계 전환(nextPhase 참고) |
| session_end | 상점 안에서 세션 종료. detail=종료 사유(application_quit, return_to_title, unknown 등). GameManager 경로는 state를 채우고, 관찰자 대체 경로는 state=null |
| reopened | 닫히지 않은 방문 위에 새 방문이 열림(정상 흐름에서는 생기지 않음) |

### 5.33 shop_view_shown / 5.34 shop_view_hidden

shown 발생: 상점 패널이 실제로 보이게 된 첫 프레임(ShopPresenter.LateUpdate). `visitId:string?`, `selection:{weaponId, partId}`, `inventory:ShopInventory?`(표시 시점 보유품).

hidden 발생: 보이던 패널이 사라질 때 한 번. `visitId:string?`, `reason:string`(shop_closed / phase_changed / presenter_disabled / not_visible / session_end), `offerSetId:string?`, `revision:int?`(마지막 제시). 퇴장 시에는 hidden(reason=shop_closed)이 shop_closed보다 먼저 온다.

### 5.35 shop_ui_input

발생: 상점 버튼 클릭(마우스·키보드·게임패드 Submit 공통) 처리 직전, 조작 한 번에 한 행. 버튼 onClick이 실제로 불린 경우만이며 비활성 버튼은 Unity가 클릭을 막아 기록되지 않는다.

`interactionId:string`, `visitId:string?`, `action:string`, `control:{placement, row:int?, label:string?, priceText:string?, interactable:bool?}?`, `targetSlot:int?`, `balance:int?`, `selection:{weaponId, partId}`(조작 직전 선택), `visitElapsedSeconds:number?`.

action: weapon_select, weapon_buy, part_select, part_buy, part_attach, part_detach, slot_card_select, akimbo_toggle, stat_buy, ammo_buy, slot_upgrade_buy, next_wave. placement은 shop_offers_presented와 같은 이름에 part_attach / part_detach / slot_card / akimbo / next_wave를 더한다. label은 화면 문구 그대로(리치 텍스트 태그 포함)다.

UI 시도와 게임 결과는 분리된다. 같은 interactionId를 가진 shop_selection_changed / shop_purchase_attempt / shop_equipment_result / shop_closed가 결과이며, 아무 결과도 없으면 shop_ui_input_ignored가 온다. 입력 행만으로 구매·장착 성공을 세지 않는다.

### 5.36 shop_ui_input_ignored

발생: 입력이 끝났는데 연결된 게임 이벤트가 하나도 없을 때. `interactionId:string`, `visitId:string?`, `reason:string`.

reason: invalid_row, no_part_selected, no_attach_source(붙일 보관·휴대 개체 없음), part_not_on_weapon, empty_slot, no_effect(예: 상점 밖에서 다음 웨이브), exception(처리 중 예외), session_end(처리 중 세션 종료), superseded.

### 5.37 shop_selection_changed

발생: 무기·파츠 선택 조작(값이 같아도 changed=false로 기록) 또는 조작 없이 선택이 바뀐 경우(자동 첫 파츠 선택 등, source=refresh). 같은 선택이 유지되는 프레임에는 쓰지 않는다.

`visitId:string?`, `interactionId:string?`, `source:string`(weapon_catalog / part_catalog / slot_card / refresh), `changed:bool`, `before:{weaponId, partId}?`, `after:{weaponId, partId}`.

### 5.38 shop_focus_changed

발생: 상점 패널이 열린 동안 EventSystem 선택 대상이 바뀐 프레임에 한 번(키보드·게임패드 탐색, 클릭에 의한 선택, 화면 코드의 자동 포커스).

`visitId:string?`, `interactionId:string?`, `cause:string`(player / programmatic), `from:ShopControl?`, `to:ShopControl?`. 상점 밖 UI는 null, 상점 안의 다른 요소는 placement=shop_other. 상점 요소 위의 마우스 포인터 호버(enter/exit)와 스크롤 위치 변화는 각각 shop_pointer_enter, shop_pointer_exit, shop_scroll_changed로 기록한다.

### 5.39 shop_equipment_result

발생: TryAttachPart / TryDetachPart(모든 오버로드) / TrySetAkimbo(TryToggleAkimbo 포함)의 가장 바깥 호출이 끝난 뒤. 무료 조작이라 구매 이벤트와 분리한다.

`actionId:string`, `visitId:string?`, `interactionId:string?`, `request:{action(part_attach/part_detach/akimbo_set), partId, partInstanceId, targetSlot, targetWeaponInstanceId, sourceWeaponInstanceId, akimbo:bool?}`, `success:bool`, `changed:bool`, `failureCode:string?`, `displayReason:string?`, `before:ShopSnapshot?`, `after:ShopSnapshot?`.

success는 함수가 빈 문자열을 반환했을 때다. changed는 before/after의 파츠 위치·휴대 무기·activeHand가 달라졌는지이며, 이미 그 상태인 아킴보 설정은 success=true, changed=false다. 예외는 failureCode=exception이고 원래 예외는 호출자에게 전파된다.

### 5.40 shop_pointer_enter / 5.41 shop_pointer_exit

발생: 상점 화면이 열려 있는 동안 마우스 포인터가 상점 버튼·카드·줄 요소에 진입(enter)하거나 벗어났을(exit) 때. 상점 화면이 닫힐 때 호버 중이던 요소는 exit를 남긴다.

`visitId:string?`, `interactionId:string?`, `control:{placement:string, row:int?, label:string?, priceText:string?, interactable:bool?}`.

### 5.42 shop_scroll_changed

발생: 상점 내 스크롤 뷰(무기 목록, 인벤토리, 보급 목록)의 위치가 이동했을 때. 플레이어 휠/드래그 완료 시(정지 2프레임 후 한 번) 또는 programmatic(화면 열림 리셋, 초점 맞춤 이동) 시 1회 기록하며, 이동 없는 프레임에는 기록하지 않는다(per-frame spam 방지).

`visitId:string?`, `interactionId:string?`, `view:string`(weapon_catalog / inventory / ammo), `previousPosition:number?`, `newPosition:number`, `before:number?`, `after:number`, `cause:string`(player / programmatic).

## 6. 순서·집계·실패 해석 규칙

### 정상·사망·경계

- 정상 웨이브: wave_start → 사건/틱 → 선택적 enemies_cleared → 사건/틱 계속 → 실제 완료 보상 → wave_summary(completed) → wave_intermission_started/shop 기록.
- 사망: 치명 player_damage → death_snapshot → 열린 웨이브의 wave_summary(interrupted) → 진행 회전/구매 incomplete → session_end. pending이 없으면 해당 행도 없다. 중단 보상은 null이다.
- 비사망 종료는 death_snapshot 없이 나머지를 마감한다. 이미 닫힌 웨이브를 다시 요약하지 않는다. 관측하지 못한 종료 사유는 unknown이며 OnDisable만으로 자진 종료라고 단정하지 않는다.
- 슬롯은 시작과 결과가 다른 단계/웨이브일 수 있다. 발사체도 발사와 명중이 다른 웨이브일 수 있다. origin을 보존하고 결과 봉투는 현재 문맥을 쓴다.
- 세션 종료 후 원래 콜백의 게임 동작 정책과 로그 수명은 별개다. 분석 세션을 재개하거나 새 세션에 섞지 않는다.

### 경제·전투 합계

- 탄약 총량 T는 공유 예비탄+휴대 장전탄+GroundRoot 미소비 바닥 장전탄이다. `T(end)=T(start)+acquired-consumed-discarded`로 교차 확인한다. 내부 재장전/반환/바닥 왕복을 획득·소비로 더하지 않는다.
- 슬롯/상점의 ammoGranted/ammoChanges를 ammo_changed와 더하지 않는다. wave_summary.ammo를 개별 변경량과 다시 더하지 않는다. 동일 사건을 보는 다른 표현이다.
- 상점/마감 후 슬롯 지급은 이미 닫힌 웨이브 탄약 합계에 넣지 않고 다음 웨이브 시작 상태에 반영한다.
- 사격은 shotId, 탄은 projectileId로 센다. 단발/산탄을 같은 shotId 의미로 다룬다. hitEnemy/actualDamage/killed를 서로 대체하지 않는다.
- 요약은 `(sessionId, summaryId)`별 최대 revision의 전체본만 사용한다. origin과 발생 wave가 다르면 소속을 명시적으로 분리한다.

### 저장 실패와 완전성

- 크기 제한/직렬화 실패는 레코드를 거부하며 실제 JSON null·유한 수치 규칙을 지킨다. NaN/Infinity는 거부한다. JSON 문자열의 한글은 유니코드 escape로 저장될 수 있다.
- 첫 저장 IO 실패 뒤 해당 세션의 저장을 멈추고 게임은 계속한다. LogSession.Diagnostics의 FailureCount/DroppedRecords/WarningCount/LastError/StorageFailed는 **메모리 진단**이며 자동으로 별도 분석 eventType을 만드는 필드가 아니다.
- 제한 경고는 Debug.LogWarning으로 출력되며 LogKit이 켜져 있으면 콘솔 경고로 관측할 수 있다. 진단/초기화 경고 문자열은 코드/예외에 따라 달라지는 메시지다.
- 기록 off는 파일을 만들지 않는다. 세션 종료 중복 방어와 저장 실패 때문에 모든 시작에 항상 끝 기록이 있다고 가정하지 않는다.
- session_end가 없으면 종료 미확인이다. 마지막 불완전 JSONL 행은 앞의 정상 행과 분리해 다루고 원본을 보존한다. 중간 손상을 정상 데이터처럼 무시하지 않는다. 디스크/OS 캐시·강제 종료의 완전한 내구성은 보장하지 않는다.

## 7. 별도 LogKit 콘솔 로그 전체 구조

이 절의 파일은 분석 봉투와 형식·sessionId·수명 모두 다르다. 패키지 소스는 `POC2/Library/PackageCache/com.team.logkit@dc5d377c4776/Runtime/`이며 캐시는 재생성될 수 있으므로 나중에는 manifest/lock과 설치된 버전을 확인한다.

### 파일 첫 줄: LogSessionHeader

`sessionId:string`, `startedAtUtc:string`, `appVersion:string`, `unityVersion:string`, `isEditor:bool`, `platform:string`.

LogKit sessionId는 현재 GUID 앞 8자리+`_`+UTC yyyyMMdd_HHmmss 형식이다. 분석 한 판 sessionId와 조인 키로 사용하지 않는다. LogKit은 DontDestroyOnLoad 로거의 수명을 따르므로 Title→Game 재시작의 한 판 경계와 같다고 보장하지 않는다.

### 이후 줄: LogEntry

| 필드 | 의미 |
|---|---|
| timestampUtc | 실제 메시지 UTC |
| level | Info/Warning/Error/Assert/Exception |
| category | 자동 콘솔 수집은 Unity |
| scene | 관측한 현재 씬 이름 |
| message | Debug.Log/LogWarning/LogError/Assert/Exception 등의 실제 메시지 |
| dataJson | 자동 콘솔 수집은 빈 문자열. 수동 API가 채우면 JSON을 담은 **문자열**이며 중첩 객체 자체가 아님 |
| stackTrace | 자동 수집에서 Error/Assert/Exception의 스택. 일반 Info/Warning은 빈 문자열 |

자동 콘솔 메시지는 프로젝트·엔진·패키지·예외가 동적으로 발생시키므로 고정된 eventType 목록이 없다. 분석 이벤트 30종을 LogKit에 복제하는 구조도 아니다. 현재 `Assets/Scripts`에는 GameLogger.Data/Count/Measure/Info/Warn/Error 직접 호출이 없고, LogKitBootstrap.Configure가 설정하며 Unity 콘솔을 수집한다.

### 패키지 보조 산출물

- 지표가 있을 때 `<id>.metrics.json`: `{metrics:[{key:string,count:long,sum:number}]}`. 패키지의 Count/Measure 기능이며 현재 게임 분석 합계의 원본이 아니다. 현재 직접 호출이 없으므로 항상 생성된다고 가정하지 않는다.
- 전송 시 `<id>.progress.json`: `{offset:long,nextPart:int}`. 업로드의 읽기 위치/다음 파트 번호다.
- 재시도·손상 격리 과정에서 `.pending`, `.corrupt` 접미사가 붙을 수 있다. 이들은 분석 이벤트가 아니라 패키지 파일 상태다.
- 업로드 요청의 UploadBatch는 header 정보에 `endedAtUtc`, `endedCleanly`, `truncated`, `partIndex`, `metrics`, `entries`를 더한 별도 전송 봉투다. Telemetry/*.jsonl의 공통 봉투로 해석하지 않는다.

현재 저장소 설정은 LogKit enabled=true, captureUnityLogs=true, flushIntervalSeconds=5, uploadEnabled=false다. 선택적 `Resources/TelemetryLocalData.json`은 명시된 필드만 덮어쓸 수 있다. 주소/키 값은 이 명세의 데이터 계약이 아니며 실제 환경 설정을 따른다. 분석 JSONL 업로드를 추가하려면 별도 기능으로 설계한다.

이벤트 추가/변경 시 작성부뿐 아니라 이 문서의 목록·필드·집계 규칙과 파일 판독기를 함께 갱신한다. 스키마 변경은 과거 schemaVersion=1과의 해석 차이까지 명시한다. 신호를 받을 새 전역 싱글턴이나 별도 시계/세션/경제 집계기를 중복으로 만들지 않는다.

현재 명세 대조는 소스의 모든 TryRecord 작성부와 LogGameplayEvents.Write의 동적 이름 6종을 포함한다. 일반 코드를 통해 새 eventType이 추가되면 이 42종은 늘어난다. 상점 로그 결정적 검사는 메뉴 POC/Verify Shop Telemetry(PocShopLogVerification), 실제 버튼 경로는 POC/Verify Shop UI (Play) 끝의 텔레메트리 검사, 저장 파일은 Tools/POC/Verify Unified Telemetry File이 방문 쌍·입력 연결까지 확인한다. 순수 서비스의 TryRecord 자체가 허용하는 임의 이벤트나 과거 검사 전용 contract_probe 등을 현재 플레이 이벤트로 추가하지 않는다.

운영·사용자 확인 절차는 [로그 시스템 운영·통합 검증](로그-시스템-운영-검증.md), 배경 기획은 [기획안](로그-시스템-기획안.md), 콘솔/분석 분리 배경은 [LogKit 적용](LogKit-로그-적용.md)을 참고한다. 과거 문서의 `.omo/verification/log-phase*`와 synthetic 샘플 경로는 현재 파일이 남아 있는지 먼저 확인한다. 이 명세는 그 산출물이 없어도 읽을 수 있게 작성했다.
