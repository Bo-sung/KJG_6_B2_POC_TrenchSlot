# 로그 데이터 형식 설계 (v1.1 — 2026-10-31, 형식·절감 범위 결정 완료 / 구현 대기)

> **[결정 2026-10-31] 형식은 현행 유지** — 별도 스키마·폴더 구조를 만들지 않는다. 실시간 수집은 FixedUpdate 현행 규격대로 두고, 절감(중복 제거) 후보만 §7에서 다룬다.
> 이전 프로젝트(상점 운영 + 야간 습격)의 로그 형식 정의안을 참고. POC2는 게임 구조가 달라 **1:1 이관 불가** — 이관분/폐기분/신설분으로 나누어 정의한다.
> POC2 로그의 존재 이유 = 성공 기준 §3-1의 1번: *"돌리고 싶어서 싸운다"를 인터뷰가 아니라 로그에서 보이는가*. 이 질문을 답하지 못하는 필드는 모두 사치다.

## 1. 구조 차이 — 왜 그대로 못 쓰나

| 축 | 이전 프로젝트 | POC2 | 결과 |
|----|----|----|----|
| 게임 흐름 | 씬 2개(상점/습격) 왕복, **상점 시작/종료 = 세션 앵커** | 단일 전장 연속, **웨이브 시작/종료 = 세션 앵커** | "상점 운영 시/습격 시" 구분 → "웨이브 중/정비 중" 구분으로 치환 |
| 핵심 객체 | 주문(quest flow): 주문 ID가 사건의 외래키 | 주문 없음.핵심 객체 = **슬롯 회전**과 **웨이브** | 주문 ID 계열 필드 전부 폐기, spinId/waveId로 대체 |
| 플레이어 제작 | 작업대 제작·총기 코드 직렬화(공유 가능한 레시피) | 제작 없음, 상점 구매 + 파츠 장착 | 총기 코드 → **무기 인스턴스 ID + 파츠 구성**으로 대체 |
| 스냅샷 대상 | 습격 중 블록/탱크/헬기 | 블록·탱크·헬기 없음 | 스냅샷은 유지하되 필드를 슬롯 관련 상태로 교체(§3) |

## 2. 항목별 대응표

### 이관 (형태 유지, 앵커만 교체)
| 이전 항목 | POC2 대응 |
|----|----|
| 상점 시작/종료 시 (시간·일수·금액) | **웨이브 시작/종료 시** — 웨이브 번호, 경과시간, 소지금, 체력, (종료 시) 클리어 성공/실패 ← "주문 완료 성공여부"의 대응이 여기 |
| 습격 시 가져간 총 (모듈 사용률) | **웨이브 시작 휴대 무기** — 슬롯 1·2의 무기 인스턴스 + 파츠 구성 + 탄종. ★"주로 쓰는 총/파츠" 집계 = 원래 의도 그대로 성립 |
| 작업대 상호작용/이탈 | **상점 UI 열기/닫기** — 시각, 웨이브, 체류시간 |
| 프리셋 저장 (총기 코드) | **무기 교체/투척/픽업** — 무기 인스턴스, 파츠 구성, 바닥 픽업 여부. 파츠가 총에 귀속된 현 설계(§상점 10)와 맞아떨어져 "바닥에서 주운 총 그대로" 검증 가능 |

### 폐기
| 이전 항목 | 사유 |
|----|----|
| 주문 ID / 작업대 / 손님 상호작용 | 객체 자체가 없음 |
| 사격 테스트 횟수 | 테스트라는 개념 없음. 근접 지표 = 유휴 사격률(웨이브 전 대기 중 발포) — 필요하면 §4 idle 이벤트로 대용 |
| 블록/탱크/헬기 수 | 미구현 대상 |

### 신설 (이전 프로젝트에 없으나 POC2가 필수)
| 이벤트 | 필드 | 증명하는 것 |
|----|----|----|
| **spin** | spinId, wave, 시각, 전/후 소지금, 조합(심볼3), 결과(당첨/2줄/꽝), 현금·현물(탄종+발수/파츠ID), +10HP, 킬스택 수 | 슬롯 경제 전체 (§1-3 v4) |
| **kill** | 시각, wave, 무기 인스턴스, 탄종, **처치 위치**, 헤드샷/저지 여부, 플레이어-적 거리 | "처치=주수입" · 무기별 킬 분포 |
| **ammo_grant / pickup** | 시각, 탄종, 발수, 출처(꽝/심볼/드랍/상점) | "탄약은 걸어다닌다" — 드랍을 주우러 뛰는가 |
| **purchase** | 시각, wave, 카테고리(스탯/무기/파츠/슬롯업/탄약), ItemId, 가격, 전/후 금액 | 채널 원칙 — 슬롯 현물 vs 상점 구매 비율 |
| **death** | wave, 시각, 총 처치 수, 소지금, 직전 구매, 피격 출처 | "한 판 더" 회로, 도달 웨이브 = 스코어 |

## 3. 고정 스냅샷 (Fixed Delta Time) — 웨이브 중

**[결정 2026-10-31] 현행 유지: 조작 가능한 매 FixedUpdate에 기록.** 0.5초 간격 제안은 폐기 — 현행 명세의 "별도 샘플 간격 금지" 규격과 충돌하며, 분석 스크립트가 이미 틱 단위 스트림 기준이다.

| 필드 | 대응 근거 |
|----|----|
| 위치(x,y,z) / 카메라 yaw·pitch | 이전 "플레이어 위치·카메라 로테이션" 그대로 — **좌우 시선 전환 강제(§1-1 레벨 의도)의 검증 데이터** |
| 체력 / 소지금 | 이전 "플레이어 체력" + POC2 화폐 |
| ~~슬롯머신까지 거리 / 슬롯 회전 중 여부~~ | **미저장 [결정 2026-10-31]** — 위치(x,z)와 슬롯 고정 좌표로 후처리 산출, 회전 중 여부는 spin 시작/결과 이벤트 구간으로 유추. 거리·회전 상태를 매 틱 중복 저장하지 않는다 |
| 잔여 적 수 / 웨이브 진행시간 | 이전 "탱크 수·헬기 수"의 자리 |

## 4. 파생 지표 (원시 로그에 저장 안 함, 후처리)

- **교차 점화 간격**: kill→최초 spin 도달시간 / spin→최초 kill. 분포의 꼬리가 "돌리고 싶어서 싸운다"의 실증
- 슬롯 근접(반경 R) 체류시간 합 / 판, 근접 후 3초 내 회전율 (§3-1 1번과 동일 계산)
- 채널 비율: 탄약 총 획득액 중 슬롯 출처 %(§2 ammo_grant 출처별) vs 상점 전량충전 구매 — 이중 가격표(§1-3)의 실측 검증 [현행 상점가 $50, §1-3 재조정 대기 연동]

## 7. 현 구현과의 관계 — 신설 5종 대응 [결정: 현행 유지]

이 문서는 로그 구현 전에 작성된 초안이라 "신설"이 대부분 이미 구현돼 있다(전체-로그-명세.md). 별도 신설 이벤트는 없다.

| 초안 신설 | 현행 대응 | 판정 |
|---|---|---|
| spin | slot_spin_started/healed/resolved/incomplete (spinId, 전/후 잔액, faces, 현물, +HP) | 충족 |
| kill | projectile_impact (killed·headshot·point·무기 인스턴스) — 처치 전용 이벤트 없음, impact로 재현 | 충족 |
| ammo_grant / pickup | ammo_changed source=drop/shop_pack/slot_reserve/slot_loaded | 충족 |
| purchase | shop_purchase_attempt/result (카테고리·전후 잔액·실패사유) | 충족 |
| death | death_snapshot + session_end(reason=death) | 충족 |
| 0.5s 스냅샷 | player_position+enemy_alive_counts (매 FixedUpdate) | 초과 — §3 결정 |

- 파생 지표(kill→spin 도달시간, 슬롯 근접 3초 후 회전율)는 **후처리 스크립트**로 정의. 저장 추가 없음 (§4)

### 중복 절감 감사 [결정 2026-10-31 — 결정 #38]

"다른 레코드의 조합으로 유추 가능한 필드/이벤트" 감사 결과와 처분:

**절감 확정** (작업 세션에서 제거 실행):
1. `weapon_bought` / `weapon_picked_up` / `weapon_dropped` → **이벤트 제거**. shop_purchase_result.createdWeaponIds·ammo_changed(source=weapon_drop/pickup)와 중복. 명세도 "두 번 세지 않는다"고 선언한 보조 관측
2. `slot_spin_requested` → **이벤트 제거**. spinId 없음·1:1 대응 없음. started+rejected로 시도 전체 재현
3. `wave_intermission_started` → **이벤트 제거**. shop_opened(intermissionSeconds·state)와 완전 중복
4. `player_shot.magazineAmmo` / `reserveAmmo` → **필드 제거**. 명세가 이미 비권위 선언, 실제 소비는 ammo_changed(같은 shotId)가 정본
5. `projectile_impact`의 weaponTypeId·hand·origin* → **유지**. shotId 조인이 정석이지만 join 없는 분석 편의용 비정규화로 남긴다 (제거 후보에서 제외)

**유지** (중복이 아니라 정책): PlayerSnapshot 중첩(틱 정지 구간 — 상점/사망 상태는 틱으로 재구성 불가), slot_spin_resolved before/after(외부 재진입 위험), session_end.totalKills(집계 경로 상이, 상호 검증용), tick weapons[](장착 이벤트 누락 시 자기완결성)

**합병 확정 [결정]**: 같은 fixedTick의 player_position + enemy_alive_counts를 **1행 1 eventType으로 합병** — 틱 레코드 절반, 정보 손실 없음. 위치+시점(yaw·pitch)은 그대로 남기므로 슬롯 거리·회전 구간은 여전히 후처리 유추 (§3).

**영향**: 게임 이벤트 42종 → 제거 5종 + 합병 1종 감소 = **36종**. player_shot에서 필드 2개 감소.

절감 실행 시: 로그 작업 세션 과업. 명세·판독기·검증 동시 갱신, payload 구조 변경이므로 schemaVersion 상향(2 권장)과 과거 파일(schemaVersion 1) 해석 차이 명시.
