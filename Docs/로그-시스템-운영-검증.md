# 로그 시스템 운영·통합 검증

작성일: 2026-10-31. 1~8차 구현 및 비Unity 검사를 완료했다. **실제 Unity 플레이·화면·파일 생성·프레임 영향은 사용자 확인 대기**다.

대표 입력은 실제 순수 서비스·수집기·AmmoInventory·PlayerWallet·FileLogStore를 실행한다. Unity의 입력, 물리 충돌, UI, ShopInfo 구매 정책, SlotRewardInfo 보상 계산을 실행한 결과는 아니다. 제어한 발생 사실과 상태를 수집기에 전달한다.

## 실행과 저장

- 분석 로그: `Application.persistentDataPath/Telemetry/<sessionId>.jsonl`. 실행 환경의 실제 persistentDataPath를 사용한다. `POC2/Logs`, 소스 `Assets/Resources`가 아니다.
- 설정 원본: `POC2/Assets/Resources/LogData.json`. TableManager가 LogData를 로드·검증하며 잘못된 설정은 진단 후 기록을 비활성화한다.
- 현재 설정: enabled=true, schemaVersion=1, deathEnemyRadius=10m, flushIntervalSeconds=2, maxBufferedRecords=256, maxBufferedBytes=1,048,576, maxRecordBytes=65,536, maxWarningsPerSession=3.
- `flushIntervalSeconds`는 세션 FixedUpdate 누적 시간 기준이다. 게임 정지 중 벽시계 2초마다 저장한다는 뜻이 아니다. 용량 한계·명시적 Flush·정상 종료도 flush한다. 틱별 생성과 flush는 별개다.
- 별도 샘플 간격·N틱 생략·로그 시간 배율 설정은 없다. 로그는 Time.fixedDeltaTime을 읽으며 값을 변경하지 않는다.
- 기록은 UTF-8 BOM 없는 JSONL이며 한 줄을 독립 JSON으로 읽는다. 파일은 새로 생성하고 기존 파일을 덮어쓰지 않는다.
- LogSession 분석 파일은 로컬 저장만 한다. LogKit은 별도 `persistentDataPath/Logs`의 콘솔·오류와 선택적 전송을 담당한다. 분석 JSONL을 자동 업로드하지 않는다. [LogKit 설명](LogKit-로그-적용.md) 참조.

## JSONL 읽는 방법

1. 파일별로 읽고 schemaVersion을 확인한다. 현재 값은 1이다. 과거 단계의 합성 계약 확인용 파일까지 현재 플레이 스키마와 같다고 가정하지 않는다. `--audit`은 현재 구현의 도메인 레코드를 대상으로 한다.
2. sessionId로 판을 분리하고 sequence 순으로 처리한다. elapsedSeconds는 FixedUpdate에서 한 번 누적한 게임 시간이며 UTC/벽시계와 다르다. 같은 틱 이벤트는 시간이 같아도 sequence로 구분한다.
3. waveNumber는 첫 웨이브 전 JSON null이다. null은 미확인/해당 없음이며 실제 0과 다르다. player_damage의 출처 미확인은 unknown이다. 위치는 월드 미터, 카메라는 yaw/pitch 각도다.
4. player_position과 enemy_alive_counts는 같은 fixedTick·elapsedSeconds의 짝이다. 조작 가능한 wave 틱만 생성한다. 상점에서도 세션 시간은 진행하지만 두 레코드는 생성하지 않는다. timeScale 정지로 FixedUpdate가 없으면 누적·기록도 없다. 기록에서 빠진 시간을 보간하지 않는다.
5. 무기 종류 weaponTypeId와 개체 instanceId/weaponInstanceId를 구분한다. 같은 개체의 바닥 왕복·슬롯 교환은 ID를 유지한다. hand는 right/left, activeHand는 both일 수 있다. shotId는 사격 묶음, projectileId는 각 탄, spinId는 회전, attemptId는 구매, transactionId는 탄약 사건이다.
6. 산탄은 player_shot 1회와 여러 projectileIds다. shots와 hitShots, projectiles와 hitProjectiles를 별도로 본다. 실제 피해 0인 접촉을 실제 체력 감소로 바꾸지 않는다. 발사 당시 출처가 이후 무기 교체·적 파괴에도 유지된다.
7. summaryId별로 revision이 가장 큰 **전체 요약 하나만** 선택한다. 원본과 보정본을 더하지 않는다. 보정 봉투 waveNumber는 발생 현재 웨이브일 수 있으므로 요약의 소속은 payload.plan.waveNumber와 summaryId를 사용한다. collectionStatus=failed/not_collected는 0이 아니다.
8. 탄약 획득 합계는 canonical ammo_changed 또는 해당 웨이브 최종 ammo 요약으로 계산한다. slot_spin_resolved.ammoGranted와 shop_purchase_result.ammoChanges는 같은 transactionId의 참조이므로 더하지 않는다. acquiredBySource의 실제량을 쓰고 팩 명목량을 더하지 않는다.
9. 탄약 보존 범위 T는 공유 예비탄+휴대 장전탄+GroundRoot 미소비 바닥 장전탄이다. `T(end)=T(start)+신규획득-발사소비-폐기`. 재장전·바닥 이동은 내부 이동이다. 범위 밖/미확인 개체나 외부 스크립트의 미관측 직접 변경은 보장하지 않는다. 마감 후 상점/슬롯 지급은 닫힌 이전 합계를 바꾸지 않고 다음 start에 반영된다.
10. 자동 빈 탄창 발사는 자격 있는 유지 입력 구간당 1회, 단발은 입력 시도당 1회다. 재장전 부족은 명시적 입력에서 예비탄 0으로 시작 못한 시도다. 쿨다운·사망·입력 차단·진행 중 재장전·다른 손 발사 가능은 부족으로 세지 않는다.
11. 상점 offerSetId는 열기별, revision은 노출 내용/잔액/선택 등의 변경별이다. 같은 Refresh는 제시 횟수를 늘리지 않는다. placement/row가 같은 제시를 식별한다. 직접 API·낡은 제시 참조는 offer=null이다. `actualSpent`와 `actualMoneyDelta`는 관측 구간 전후의 순잔액 차이다. 같은 구간의 외부 재진입 거래가 있다면 그 영향도 포함될 수 있다.
12. 슬롯의 faces/symbolIds는 원본 릴이다. plannedPartIds는 지급 계획이며 실제 생성 파츠 증거로 쓰지 않는다. incomplete는 보상 0 확정이 아니다. 구매도 세션 종료 중에는 shop_purchase_incomplete로 남을 수 있다.

정상 사망 순서는 `death_snapshot → 열린 wave_summary(interrupted) → 진행 중 회전/구매 incomplete → session_end`다. 정상 완료 보상은 실제 지급 후 기록한다. 사망 중단의 bonusPaid/healthRestored는 null이다. session_end가 없으면 종료 미확인이며 종료 사유·완료 보상을 추측하지 않는다.

디스크 쓰기 실패 시 게임 진행을 중단하지 않고 해당 세션 저장을 멈춘다. 최대 크기를 넘는 레코드는 거부되고 진단을 남긴다. 버퍼·OS 캐시·강제 종료 때문에 유실될 수 있으며 session_end 존재만으로 기록의 완전한 내구성이나 실제 게임플레이의 정확성을 보장하지 않는다. 파일은 종료 후 복사해서 분석한다.

## 합성 예시와 검사 실행

[8차 대표 JSONL](로그-시스템-8차.synthetic.jsonl)은 실제 FileLogStore가 임시 디렉터리에 쓴 파일을 복사한 **synthetic** 예시다. session_start.buildVersion은 synthetic-phase8, mapId는 synthetic-map이며 UTC는 고정 입력이다. 무기/탄종/팩 가격/회전 비용은 현재 Resources 테이블에서 읽지만 명중·보상량·구매 결과·적 종류는 제어 입력이다. 슬롯 outcome은 보상 평가기를 재현하지 않는다.

대표 흐름은 시작→웨이브1→양손 사격→fixedDeltaTime 변경/정지·재개 모델→unknown 피해→드롭/재장전/바닥 교환→산탄·조기 전멸→전멸 후 틱→슬롯 지급→정상 보상→상점으로 넘어간 슬롯 지급→탄약 구매/실패→웨이브2→웨이브1 발사체 늦은 명중·보정→진행 회전/구매가 있는 사망→종료다.

대표 결과는 61줄, 조작 가능 6틱의 위치/적 수 각 6개, 경과 시간 0.26초다. 사격 묶음 4회, 적중 발사체 4개, 사격 명중 묶음 3회, 중복 제외 처치 2회, 실제 가한 피해 합계 8이다. 웨이브1 획득은 7발, 소비는 4발, 재장전 내부 이동은 2발이다. 상점 단계의 추가 지급/구매는 이 합계에 포함하지 않는다. 늦은 명중의 revision=1을 채택하며 원본 revision=0은 보존한다.

저장소 루트에서 실행한다. .NET 10 SDK와 현재 프로젝트의 캐시된 Newtonsoft.Json 어셈블리가 필요하다. 외부 컴파일 프로젝트는 기존 Unity 생성 csproj/참조 어셈블리에도 의존한다. Unity를 실행하는 명령은 포함하지 않는다.

```sh
dotnet run --project .omo/verification/log-phase8/LogPhase8.csproj --verbosity quiet
dotnet run --project .omo/verification/log-phase8/LogPhase8.csproj -- --audit "Docs/로그-시스템-8차.synthetic.jsonl"
dotnet run --project .omo/verification/log-phase8/LogPhase8.csproj -- --audit "<실제 persistentDataPath>/Telemetry/<sessionId>.jsonl"
dotnet build .omo/verification/log-phase8/CompileRuntime.csproj --nologo --verbosity quiet
dotnet build .omo/verification/log-phase8/CompileEditor.csproj --nologo --verbosity quiet
```

`--audit`은 스키마·연속 sequence·동일 세션·단조 시간·틱 짝·사격/탄/회전/구매 ID·제시 참조·canonical 탄약·잔액 차이·요약 개정 체인을 검사한다. 참조 검사 때문에 파일을 메모리에 읽으며 대용량 분석용 스트리밍 엔진은 아니다. 실제 명중/가격 판정/보상의 정답까지 판정하지 않는다. `latestSummaries`는 최고 개정본만 보유하고, 경제 보존식/집계 교차 검사는 대표 입력 검사에서 별도로 수행한다.

마지막 줄에 개행이 없고 객체 JSON 파싱에 실패하면 그 줄을 격리하고 유효 앞부분을 검사한다. 원본을 수정하지 않으며 `quarantinedTail=True`, `endConfirmed=False`로 보고한다. 이것만으로 강제 종료 원인을 확정하지 않는다. 정상 JSON 마지막 줄은 개행 없이도 인정한다. 중간 손상·개행으로 마감된 잘못된 행은 실패한다. `STRUCTURE PASS`와 `endConfirmed=False`가 함께 나오면 유효 앞부분의 구조만 통과한 종료 미확인 세션이다. 미완료 spin/attempt는 이런 파일에서 결과를 추정하지 않는다.
