# 로그 시스템 5차: 탄약 수급·소모·부족

구현일: 2026-10-31. Unity 실행 및 Unity API 실행 검증은 하지 않았다.

## 소유자와 출력

`GameManager.Logging`이 세션별 `LogAmmoCollector`를 만들고 기존 `LogGameLifecycle`에 Key=ammo로 등록한다.
웨이브 시작과 정상/중단 마감 시 `CaptureLogAmmo`를 호출해 값으로 복사한다.
공통 시계·저장소·sequence를 재사용하며 별도 파일 쓰기나 시간 누적을 하지 않는다.
기존 combat 요약·LogKit 콘솔 수집과 독립된 중복 게임 로거를 만들지 않는다.

`wave_summary.payload.summaries.ammo`는 collectionStatus와 data를 가진다.
data는 start, end, ammoTypes다. 스냅샷 수집 실패는 failed/null이며 수집하지 못한 양을 0으로 꾸미지 않는다.

- start/end.reserves: 테이블 탄종별 ammoTypeId, reserve, maximum.
- start/end.weapons: instanceId, weaponTypeId, ammoTypeId, location(carried/floor), 활성 hand, 휴대 slot, loadedAmmo.
- ammoTypes: 탄종별 consumed, discarded, reloaded, moved, emptyFireAttempts, emptyReloadAttempts, acquiredBySource.
- 테이블의 알려진 탄종은 사용하지 않아도 수집된 0 합계를 출력한다. 알 수 없는 무기 탄약량·손·슬롯은 null이다.
- acquiredBySource의 출처가 없으면 그 출처는 관측되지 않은 것이다. 관측한 최대 상태의 0발 지급은 해당 출처=0으로 보존한다.

## 개별 사건과 실제량

`ammo_changed` payload:
transactionId, causeId, source, ammoTypeId, weaponInstanceId, hand, shotId,
reserveDelta, loadedDelta, acquired, consumed, discarded, transferred, moved,
reserveMaximumBefore, reserveMaximumAfter.

transactionId는 별도 AmmoTransaction ID 공간에서 발급한다.
causeId는 연관 사건 그룹이며 향후 spinId/purchaseAttemptId를 전달할 수 있다. 같은 causeId라고 서로 다른 손의 지급을 제거하지 않는다.
금액·회전 수집기가 이 이벤트를 다시 합산하지 않는다. 탄약 경제 합산의 단일 소유자는 이 수집기다.

| source | 실제량 산출 지점 | 집계 |
|---|---|---|
| shot | TakeShot 직전/직후 해당 손의 차이 | consumed, loadedDelta. 기존 LogShotContext의 shotId/weaponInstanceId/hand 재사용 |
| reload | Consume 반환값과 실제 손 장전 후 | reserveDelta=-n, loadedDelta=+n, transferred=n. 획득/소모 아님 |
| drop | AmmoInventory.Add의 실제 상한 적용량 | reserve 증가와 acquired |
| shop_pack | AmmoShop의 실제 Add | 현행 JSON 가격·현재 최대량 보충 유지, 실제 acquired만 집계 |
| slot_reserve | SlotRewardInfo.Apply의 실제 Add | 계획량이 아닌 실제 acquired |
| slot_loaded | GrantSlotAmmo의 손별 전후 차이 | 사용 중인 오른손/왼손 장전탄 직접 지급. 예비탄 차감 없음 |
| initial_weapon | 초기화된 휴대 무기를 세션 시작 후 관측 | 웨이브 이전 기록. 첫 시작 스냅샷의 기준량 |
| new_weapon | 구매 후 loadout.Put 확정 | 생성된 기본 장전탄의 신규 획득 |
| world_weapon | Weapon이 없는 바닥 프리팹의 Consume 성공 후 개체 생성분 확정 | 새로 물질화한 장전탄 신규 획득 |
| weapon_drop / weapon_pickup | 실제 스폰/픽업 Consume 성공 | moved만 집계. 바닥 왕복은 acquired/consumed 아님 |
| capacity_return | GameManager의 파츠 변경 탄창 축소 시 Add 반환값 | 예비탄 이동. 신규 획득 아님 |
| capacity_shrink | 탄창 감소량과 실제 반환량 차이 | loadedDelta 감소, 반환되지 못한 탄만 discarded |
| maximum_changed | SetMaximum이 성공한 실제 전후량 | 최대량 전후와 실제 예비탄 폐기. 최대 증가 자체는 획득 아님 |

양손 합계 HUD 수치로 발사 소비를 구하지 않는다. 산탄 발사체 수를 곱하지 않고 탄 절감 발동은 consumed=0이다.
일반/한 발씩/양손 재장전은 실제 완료한 각 이동만 집계한다. 예약 시간·취소 시점에는 탄을 미리 추가하거나 재소비하지 않는다.
슬롯 보충으로 진행 장전이 끝나는 기존 정책도 유지한다.

PlayerWeapon의 Configure/UpdateSettings가 직접 탄창을 잘라내는 경로도 실제 폐기를 관측한다.
GameManager.RefreshWeaponStats가 먼저 반환·폐기를 끝낸 경우 후속 clamp는 변화가 없어 다시 세지 않는다.
기존 게임 정책에 없는 반환을 새로 지급하지 않는다.

## 관측 API와 다음 차수

- AmmoInventory.AmmoLog: 원인 있는 Add·최대량 변경 관측. Changed의 부호로 출처를 추정하지 않는다.
- Add(id, amount, source, causeId): 실제 증가량 반환. 유효 탄종의 0발 증가도 관측한다.
- Consume: 기존 반환값·Changed 의미 유지. 현재 호출자인 PlayerWeapon이 실제 장전과 함께 한 번 기록한다.
- AmmoShop.TryBuy(id, causeId), SlotRewardInfo.Apply(..., causeId): 선택적 원인 전달.
- 기존 무인자 GrantSlotAmmo() 유지. GrantSlotAmmoForCause(causeId)는 동일 동작에 원인을 전달한다.
- Collector.Change / Shot / Reload / Weapon / Shrink / NewCauseId는 공통 세션에만 전달한다.
- collector.Shot은 실제 성공 사격 경로 한 곳에서만 호출한다. 슬롯·상점 결과 수집기가 탄약을 별도로 재집계해서는 안 된다.

현재 슬롯 게임플레이는 현물 보상의 예비탄 Add를 사용한다.
GrantSlotAmmo API의 직접 장전 보충도 관측하지만, 이 로그를 발생시키려고 기존 슬롯 보상 정책을 바꾸지 않았다.
6차의 spinId, 7차의 purchaseAttemptId 자체와 거래 상세 계약은 아직 구현하지 않았다.

## 부족 집계 단위

`ammo_shortage`는 ammoTypeId와 kind(fire/reload)를 기록한다.

- 자동 연사: 실제 유지 입력 구간에서 처음 자격을 갖춘 빈 탄창 실패 1회. 버튼을 놓으면 초기화한다. 같은 유지 구간에서 장전/발사를 거쳐도 추가 부족으로 세지 않는다.
- 단발: WasPressedThisFrame의 실제 입력 시도마다 1회.
- 재장전: 명시적 Reload 입력에서 장전 필요·진행 장전 아님·예비탄 0일 때 1회.
- 발사: 모든 사용 손이 비었고 발사 설정·쿨다운이 허용하는 손이 하나 이상일 때만 부족이다.
- 다른 손에 탄이 있거나 쿨다운만 대기 중이면 부족이 아니다.
- 사망·InputGate 차단·컴포넌트 비활성·카메라 없음·진행 재장전·픽업 입력 우선 처리는 부족 집계에서 제외한다.
- 입력 차단/비활성/사망은 유지 구간을 종료한다. 공통 시간 정지 중의 Update 입력 정책은 기존 게임과 같다.

## 보존식과 웨이브 경계

탄종별 T = 공유 예비탄 + 휴대 무기의 장전탄 + GroundRoot 아래 활성·미소비 바닥 무기의 장전탄.

관측이 완전한 구간에서는:

`T(end) = T(start) + 신규 acquired 합계 - consumed - discarded`.

재장전·capacity_return은 내부 이동이다. 바닥 드롭/재획득도 내부 이동으로 T를 바꾸지 않는다.
moved는 경계를 넘긴 탄 수이며 드롭+재획득 왕복이면 두 이동이 합산된다. 신규 자원량이 아니다.
원래 WeaponInstance를 유지하므로 바닥 왕복/휴대 슬롯 교환에도 instanceId가 유지된다.

GroundRoot 밖의 외부 무기·아직 WeaponInstance가 없는 프리팹의 장전탄은 알려진 보존식 범위 밖이다.
후자는 loadedAmmo=null이며 픽업 확정 때 생성된 탄을 world_weapon으로 기록한다.
외부 스크립트가 직접 Magazine을 수정하거나 관측 API 없이 예비탄을 이동하면 이 보존식을 보장하지 않는다.
현재 프로젝트의 모든 탄약 변경 경로를 검색해 연결했다. UI·사격·AI·가격·파츠 정책은 유지한다.

정상/사망/나가기 마감에서 탄약 요약을 한 번 닫는다. 사망은 바닥 무기 정리 전 스냅샷이다.
상점 구매·웨이브 종료 후 슬롯 지급은 개별 ammo_changed로 남고 닫힌 합계는 수정하지 않는다.
그 변화는 다음 웨이브 start에 반영된다. 세션 종료 후에는 기록하지 않는다.
사망 후 씬 정리로 사라지는 자원을 진행 웨이브의 소비/폐기로 추가 계산하지 않는다.

## 비Unity 검사와 사용자 확인

실행 명령·결과는 이 문서와 프롬프트의 5차 진행 기록, `.omo/verification/log-phase5/RESULTS.md`에 남긴다.
합성 JSONL은 `Docs/로그-시스템-5차.synthetic.jsonl`이다.

사용자 Unity 확인:

1. 실제 발사·탄 절감·산탄·아킴보에서 손별 소비와 shotId 연결을 확인한다.
2. 일반/한 발씩/양손 부분 재장전 후 취소, 슬롯 보충 후 장전 종료에서 예비탄+장전탄이 보존되는지 확인한다.
3. 드롭 부분 획득/최대 상태, 현행 팩 구매, 슬롯 예비탄·직접 장전 API에서 실제 증가량과 출처를 비교한다.
4. 같은 무기의 바닥 왕복·휴대 슬롯 전환에서 ID와 장전탄이 유지되고 acquired가 늘지 않는지 확인한다.
5. 파츠 탄창 축소의 반환/상한 폐기 및 최대량 강화에서 실제량을 비교한다.
6. 자동 빈 탄창 유지/놓고 재입력, 단발 여러 입력, 명시적 Reload, 쿨다운·다른 손·사망·차단 입력의 제외를 확인한다.
7. 정상 마감·사망/나가기, 상점 구매·웨이브 후 슬롯 지급, 재시작, 비활성화에서 요약·다음 시작량·세션 분리가 맞는지 확인한다.
