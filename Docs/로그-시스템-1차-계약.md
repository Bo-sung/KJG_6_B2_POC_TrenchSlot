# 로그 시스템 1차 계약

작성일: 2026-10-31. 범위: 설정·직렬화·시계·ID·저장 기반. 실제 게임 이벤트 연결은 2차 이후다. 원 기획의 추가 확정 사항이 아니라 이번 구현에서 채택한 계약이다.

## 설정과 의존성

`POC2/Assets/Resources/LogData.json` → `LogData` → `LogInfo.TryValidate` → `TableManager.Instance.Log` 순서로 읽는다. 기존 테이블 로더의 JsonUtility는 단순 설정 읽기에만 사용한다. nullable·사전·다형 페이로드가 필요한 JSONL 출력은 기존 Newtonsoft.Json을 재사용한다. packages-lock의 `com.unity.nuget.newtonsoft-json`은 3.2.2이며 이미 런타임 참조와 캐시 DLL이 존재한다. 새 패키지나 manifest 변경은 없다. 이 전이 의존성을 제거하는 패키지 정리 작업을 한다면 로그의 Newtonsoft 참조도 함께 보존해야 한다.

| 필드 | 채택값 | 의미 |
|---|---:|---|
| enabled | true | 수집 연결 후 저장 활성화. 설정만으로 세션을 만들지 않는다 |
| schemaVersion | 1 | 양의 정수 |
| deathEnemyRadius | 10 | 후속 사망 스냅샷의 제안 반경(m) |
| flushIntervalSeconds | 2 | 공통 고정 시계 기준 flush 간격 |
| maxBufferedRecords | 256 | 공통 서비스의 대기 레코드 상한 |
| maxBufferedBytes | 1048576 | UTF-8 문자열과 줄바꿈을 합친 대기 바이트 상한 |
| maxRecordBytes | 65536 | 레코드 한 줄과 줄바꿈의 상한 |
| maxWarningsPerSession | 3 | 세션별 진단 콜백 호출 한도 |

반경·간격은 양수/유한, 버퍼·경고 수는 양수이며 한 레코드가 버퍼에 들어가야 한다. 누락/잘못된 설정은 TableManager에서 오류를 남기고 비활성화한다. 서비스도 설정을 다시 검증하고 복사해 보관하므로 실행 중 원본 테이블 수정으로 계약이 변하지 않는다. 잘못된 설정 자체는 경고 한 번만 허용한다. 0·1 및 ID/개정 증가값은 형식과 상태 전이의 의미이며 조절용 운영 수치가 아니다.

## 저장과 봉투

경로는 `Application.persistentDataPath/Telemetry/<sessionId>.jsonl`이다. 플랫폼의 절대 루트만 받고 하위 디렉터리는 고정하며 파일명은 정규화한 GUID N 형식만 허용한다. 외부 문자열로 경로나 파일명을 지정하지 않는다. 기존 세션 파일은 CreateNew로 덮어쓰지 않는다. UTF-8 BOM 없이 LF로 끝나는 JSON 한 줄을 저장한다. 한국어는 유니코드 이스케이프로 저장하고 파싱하면 원문이 복원된다. 제어 문자·따옴표·역슬래시는 JSON 이스케이프한다. 숫자는 문화권 독립이며 NaN/Infinity는 레코드 오류로 격리한다. 네트워크 전송은 없다.

| 공통 필드 | 계약 |
|---|---|
| schemaVersion | 설정의 스키마 버전 |
| eventType | 발생 사실의 종류. 비어 있으면 거부 |
| sessionId | 서비스 생성 시 새 GUID N 형식 |
| sequence | 직렬화·버퍼 수용에 성공한 레코드에 1부터 부여. 같은 틱도 별도 순서 |
| elapsedSeconds | 세션 고정 시계의 double 초 |
| waveNumber | 첫 웨이브 전 실제 JSON null. 이후 양의 정수 |
| phase | 발생 당시 단계. 미지정은 unknown |
| payload | 객체·배열·사전·스칼라·실제 JSON null 지원 |

관측하지 못한 값은 null/unknown이며 실제 0과 구분한다. `TryRecord` 호출 중 페이로드를 직렬화해 값으로 고정한다. 수집기는 Unity 객체나 그 참조를 페이로드로 전달하지 않고 메인 스레드에서 숫자·문자열·배열/DTO로 복사해야 한다. `LogRecord`, `LogJson`, `LogClock`, `LogStore`, `LogSession`, `LogSnapshots`, `LogData`, `LogInfo`는 UnityEngine 참조가 없다.

실제 파일 저장소로 생성한 예시는 `Docs/로그-시스템-1차.synthetic.jsonl`이다. `contract_probe`는 검사용이며 게임 이벤트가 아니다. 이 파일의 모든 레코드는 합성 입력이다. `fixed_delta_time_changed`도 이 예시에서는 합성 시간 입력으로 생성됐다. session_start/session_end가 없으므로 완료된 플레이 세션으로 분석하면 안 된다.

## 시간과 Unity 연결 소유권

`LogUnityAdapter.CreateSession()`은 메인 스레드에서 설정, persistentDataPath, 실제 Time.fixedDeltaTime을 읽고 순수 서비스를 만든다. 최초 fixedDeltaTime은 누적 없이 보관한다. 아직 게임 코드에서는 이 메서드를 호출하지 않는다. Preload/Title/테이블 로드는 세션이나 파일을 만들지 않는다.

2차에서 GameManager 또는 하나의 전용 소유자가 Game 모델 초기화 후 첫 웨이브 전에 서비스를 한 번 생성해야 한다. session_start에는 `StartedUtc`, `FixedDeltaTime`, 확인 가능한 버전/맵 정보를 넣는다. 생성 자체가 session_start를 출력하지는 않는다. 종료 UTC는 `ReadUtc()`를 읽는다. UTC는 `ILogUtcClock`으로 주입할 수 있고 ISO 8601 UTC Z 형식이다.

같은 소유자가 각 실제 FixedUpdate에서 `LogUnityAdapter.AdvanceFixedUpdate(session)`을 정확히 한 번 호출하고, 그 뒤 틱 수집기가 `ElapsedSeconds`를 읽는다. 어댑터는 Time.fixedDeltaTime을 변경하지 않는다. 서비스의 `LogFixedClock`만 값을 한 번 누적한다. 순수 검사에서는 `LogSession.AdvanceFixedUpdate(double)`에 실제 틱 입력을 주입한다. 상점에서도 호출하며, FixedUpdate가 실행되지 않는 정지 구간에는 호출하지 않는다. 재개 시 밀린 틱을 추정해 넣지 않는다. 같은 렌더 프레임의 여러 고정 틱도 각각 호출한다.

값이 달라지면 새 틱을 누적한 시각으로 `fixed_delta_time_changed`를 한 번 생성한다. payload는 `previousFixedDeltaTime`, `fixedDeltaTime`이다. 한 틱 안 이벤트는 같은 시간을 읽고 sequence로 구분한다. 별도 샘플 간격·시간 배율은 없다. flush 간격은 디스크 쓰기만 조절하며 틱을 생략하거나 합치지 않는다. 초기값을 주입하지 않은 순수 서비스는 첫 실제 틱의 값을 최초 관측값으로 사용한다.

## 후속 수집기가 사용할 API와 값 계약

- `SetContext(int? waveNumber, string phase)`: 발생 단계/웨이브 지정. 이전 웨이브의 늦은 결과여도 봉투에는 현재 발생 단계를 유지한다.
- `TryRecord(string eventType, object payload)`: 수집 사실을 공통 버퍼로 전달한다. true는 버퍼 수용 또는 flush 성공을 뜻하며 영구 저장 보증이 아니다. false일 때 게임 보상/구매를 취소하지 않는다.
- `NewId(LogIdKind)`: Weapon, Shot, Projectile, Spin, PurchaseAttempt별 독립 증가 ID. 형식은 `<sessionId>:<종류 소문자>:<번호>`다. 단발/산탄 모두 성공 사격당 새 Shot ID, 발사체당 별도 Projectile ID를 사용한다. spinId·attemptId를 shotId로 대체하지 않는다.
- `GetWeaponId(object weaponInstance)`: 실제 WeaponInstance 참조별 안정 ID. ConditionalWeakTable로 참조 동일성을 사용한다. 슬롯/바닥 이동 시 같은 모델을 넘기고 새 모델을 만들어 ID를 복제하지 않는다. 세션 간에는 ID를 재사용하지 않는다.
- `LogPlayerSnapshot`: nullable health/money, activeHand/activeSlot, position, weapons, reserves. `LogPosition3`은 nullable x/y/z다. `LogWeaponSnapshot`은 instanceId/weaponTypeId/ammoTypeId/hand/slot/active/loadedAmmo/partIds를 가진다. 활성 양손과 휴대 슬롯은 각각 별도 원소로 남긴다. `LogReserveSnapshot`은 탄종별 reserve/maximum이다. right/left 문자열과 실제 손 인덱스 매핑 확인은 4차에서 한다.
- `TryCloseSummary(wave, out summaryId)`: 웨이브당 논리 마감 한 번. 키는 `<sessionId>:wave:<번호>`, 원본 revision은 0이다. 정상/중단 모두 같은 경계를 사용한다. 이 API는 보상을 주거나 요약을 자동 출력하지 않는다.
- `TryReviseSummary(wave, out summaryId, out revision)`: 이미 마감된 웨이브만 같은 키에 1부터 개정 번호를 부여한다. 후속 수집기는 `wave_summary_correction`에 완전한 대체 요약을 출력해야 한다. 원본 파일/요약을 덮어쓰지 않으며 분석기는 키별 마지막 개정만 합계에 사용한다. 이 번호 예약 역시 저장 보증은 아니다.
- `LogSummaryReference`: summaryId/waveNumber/revision/collectionStatus. 미연결 수집기는 `collectionStatus = "not_collected"`와 null 요약을 사용한다. 사용하지 않은 수집기를 0으로 채운 완성 요약으로 출력하지 않는다. 실제 누적/집계 등록과 요약 생성은 2차 이후다.
- `Flush()`, `Dispose()`: 명시적 저장 및 종료 정리. Dispose는 중복 호출해도 한 번만 정리하고 이후 기록/ID/요약 변경·시간 누적을 거부한다. 저장소의 소유권은 서비스에 있다.

웨이브 경계 이후 발사체/슬롯 결과는 payload에 originWaveNumber/originPhase와 원래 shotId/spinId를 유지한다. 닫힌 요약을 바꾸어야 하면 보정 레코드를 사용한다. 상점 거래는 닫힌 웨이브 합계에 추가하지 않고 다음 시작 상태에 반영한다. 세션 종료 뒤 콜백은 캡처한 옛 서비스로 전달해 거부되게 하고 전역의 새 세션으로 라우팅하지 않는다.

2차 종료 소유자는 값 스냅샷 확보 → 필요한 중단/완료 요약 → session_end → Dispose 순서를 보장해야 한다. 사망의 상세 순서는 death_snapshot → 중단 요약 → session_end다. domain 이벤트는 이번 단계에서 자동 생성하지 않으므로 실제 세션/웨이브/사망 수집이 구현됐다고 해석하지 않는다.

## 버퍼·실패 정책

모든 API는 메인 스레드 단일 소유자용이며 스레드 안전을 제공하지 않는다. 백그라운드 작업이나 Unity 오브젝트의 작업 스레드 접근은 없다. 디스크 flush는 동기식이다. 파일은 최초 실제 쓰기 시 한 번 열어 종료까지 유지한다. 과거 레코드를 재직렬화하지 않고 대기 문자열만 순서대로 쓴다.

레코드/바이트 상한 직전에는 기존 버퍼를 flush하고, 상한에 도달하면 즉시 flush한다. 시간 간격 도달과 명시적 종료에도 flush한다. 정지 중 자동 flush 호출도 없지만 명시적 Flush/Dispose는 가능하다. 메모리 저장소도 생성자 capacity로 한도를 지정하며 검사 전용이다. 파일 저장 전의 순간적인 페이로드 직렬화 할당까지 maxBufferedBytes로 보장하는 것은 아니다.

저장소 생성·append·flush·dispose 예외는 서비스가 격리한다. 첫 저장 실패 후 해당 세션의 저장을 중단하고 버퍼를 비운다. 부분 쓰기 뒤 무분별하게 재시도해 중복 레코드를 만들지 않는다. 직렬화 오류/너무 큰 레코드는 해당 레코드만 거부하며 다음 정상 기록은 계속된다. 진단 콜백의 예외도 게임 호출부로 전파하지 않는다.

`Diagnostics`의 FailureCount, LastError, StorageFailed, DroppedRecords, WarningCount로 상태를 확인한다. DroppedRecords는 직렬화 거부와 저장 실패 당시 대기 레코드의 잠재 손실 수다. 일부가 디스크에 이미 기록됐는지 확정할 수 없으므로 정확한 미저장 행 수는 아니다. 비활성/종료/저장 중단 뒤의 거부 호출은 추가 손실 수에 넣지 않는다. Unity 어댑터는 제한된 Debug.LogWarning으로 진단한다. 일반 Debug 로그는 JSONL과 분리된다.

게임 진행·탄약·구매·보상 정책은 변경하지 않는다. 디스크 손실·강제 종료 때 마지막 버퍼와 파일 끝 한 줄이 유실될 수 있고 OS 수준 영구 저장/fsync를 보장하지 않는다. session_end가 없는 세션은 종료 미확인이다. 실제 성능·프레임 영향은 Unity 사용자 검증 대상이다.

## 검증과 사용자 확인

`.omo/verification/log-phase1/RESULTS.md`에 명령과 결과를 기록했다. 순수 실행 검사는 System.Text.Json으로 실제 출력 한 줄씩 독립 파싱한다. 전체 런타임 컴파일은 기존 Unity 어셈블리를 참조만 하며 Unity 프로세스/API를 실행하지 않는다.

사용자 확인 대기: Unity에서 새 파일/폴더 meta와 기존 Newtonsoft 참조의 import/컴파일 확인, Preload에서 LogData 로드 오류가 없는지 확인. 이번 단계는 게임 수집 미연결이므로 Play만으로 Telemetry 파일이 만들어질 것을 기대하지 않는다. 실제 Game 세션 시작/종료·persistentDataPath 파일 생성·정지/재개 확인은 2차 연결 이후에 수행한다.
