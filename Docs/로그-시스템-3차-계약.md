# 로그 시스템 3차 계약

작성일: 2026-10-31. 범위: 조작 가능한 매 FixedUpdate의 현재 위치·카메라·활성 무기와 적 종류별 생존 수. 기존 세션·시간·저장소와 2차 사망 스냅샷 API를 재사용한다. Unity 실행 검증은 사용자 확인 대기다.

## 호출과 시간

GameManager.Logging.cs의 기존 단일 FixedUpdate에서 `Telemetry.AdvanceFixedUpdate(Time.fixedDeltaTime)`을 먼저 실행하고 `CaptureLogFixedTick`을 호출한다. 시계는 기존 LogFixedClock 한 곳에서만 누적한다. 새 `TickCount`/`LogSession.FixedTick`은 각 실제 누적 호출마다 하나씩 증가하는 세션 내 고정 틱 번호다. 시간이나 렌더 프레임에서 추정한 번호가 아니다.

`LogFixedTickCollector`는 기존 경과 시간을 읽고 두 레코드를 공통 저장 버퍼에 전달한다. 같은 FixedTick을 두 번 기록하지 않으며 이동량·렌더 프레임 번호·별도 타이머로 틱을 생략하지 않는다. 최초 고정 틱 전에는 기록하지 않는다. 같은 렌더 프레임의 여러 FixedUpdate는 각각 다른 fixedTick과 실제 누적 시각을 갖는다.

조작 불가/상점에서도 세션 시계와 FixedTick은 진행한다. 따라서 위치 레코드의 fixedTick이 연속하지 않을 수 있으며 그 구간을 누락된 이동이라고 단정하면 안 된다. Time.timeScale 정지 등으로 FixedUpdate 자체가 없으면 시계·번호·수집이 모두 멈춘다. 재개 후 실제 호출부터 이어가고 정지 구간의 틱이나 좌표를 만들어 채우지 않는다. 실제 fixedDeltaTime 변경은 기존 공통 서비스가 반영/기록한다. 로그 전용 시간 배율·별도 수집 간격은 없다.

## 조작 가능 조건

다음 조건을 모두 만족할 때만 두 레코드를 생성한다.

- 세션이 활성이고 저장 가능하며, 현재 웨이브가 열린 상태이고 공통 phase가 wave다.
- 실제 GameManager 단계가 Wave이고 PlayerHealth가 존재하며 살아 있다.
- PlayerMovement가 존재하고 `IsControlEnabled`다. 이 읽기 전용 값은 컴포넌트 활성 상태, CharacterController 존재/활성, InputGate.PlayerEnabled 및 이동 컴포넌트가 참조하는 체력의 생존 상태를 확인한다.

이동/시점 입력값이 0이어도 위 조건이 참이면 기록한다. 슬롯 회전 여부나 적 전멸 여부로 차단하지 않는다. 조기 전멸 뒤에도 실제 시간 종료로 웨이브가 닫히기 전까지 계속 기록한다. 상점·사망·입력 차단·이동 컴포넌트/컨트롤러 비활성에서는 위치/적 수를 생성하지 않는다. 저장 비활성화·저장 실패 후에도 틱별 Unity 스냅샷 조회를 건너뛴다.

PlayerMovement의 기존 Update/입력/이동 동작은 변경하지 않았다. PlayerWeapon에는 실제 조준 카메라를 읽는 AimCamera getter만 추가했다. 슬롯·사격·보상·입력 정책과 씬/프리팹에는 변경이 없다.

## 레코드

공통 봉투의 sessionId, sequence, elapsedSeconds, waveNumber, phase는 기존 계약이다. 한 고정 틱에서는 다음 두 레코드를 이 순서로 별도로 남긴다.

| eventType | payload |
|---|---|
| player_position | fixedTick, player |
| enemy_alive_counts | fixedTick, enemies |

정상 저장 경로에서 두 레코드는 같은 fixedTick·elapsedSeconds·웨이브·phase를 사용하고 별개의 연속 sequence를 갖는다. 디스크 flush가 두 줄 사이에서 발생해도 합치거나 틱을 건너뛰지 않는다. 저장 실패/너무 큰 레코드 등은 기존 실패 정책을 따르며 두 줄의 디스크 저장을 원자적으로 보장하지는 않는다.

`LogPlayerTickSnapshot`의 player 필드:

| 필드 | 의미 |
|---|---|
| x, z | 현재 PlayerHealth 오브젝트의 월드 좌표(m) |
| yaw, pitch | 실제 PlayerWeapon.AimCamera의 월드 transform.eulerAngles.y/x(도) |
| activeHand | right/left/both, 확인 불가면 null |
| activeSlot | 현재 휴대 슬롯 인덱스, 확인 불가면 null |
| weapons | 현재 손에 든 무기만 포함하는 LogHeldWeaponSnapshot 배열 |

카메라 각도는 Unity가 읽어 준 Euler 값 그대로이므로 일반적으로 0~360 표현이며 위쪽/아래쪽 부호 각도로 재해석하지 않는다. 카메라가 없으면 yaw/pitch는 실제 JSON null이다. 다른 카메라나 플레이어 몸 회전으로 대체하지 않는다.

`LogHeldWeaponSnapshot`은 instanceId/weaponTypeId/hand/slot을 갖는다. PlayerWeapon.Hand(0)/Hand(1)을 실제 right/left로 조회하고 1차의 참조별 GetWeaponId를 재사용한다. 두 손에 같은 종류를 들어도 개체 ID는 각각 다르다. 매 틱 전체 휴대 무기·파츠·예비탄을 복제하지 않는다. PlayerWeapon 자체가 없으면 weapons=null이며, 존재하지만 손에 무기 모델이 없으면 빈 배열이다.

`enemies`는 2차 `LogEnemySnapshot`이다. aliveCount와 aliveByKind는 동일 생존 목록을 한 번 읽어서 계산한다. 틱 수집은 사망 반경 집계를 요청하지 않으므로 nearbyAliveCount/radius는 null이다. WaveController가 없으면 enemies=null이며 실제 생존 0으로 꾸미지 않는다.

## 종류별 생존 수 소유자

WaveController가 `LogEnemyPopulation`을 보유한다. Begin에서 수가 양수인 예정 종류로 종류 집합을 새로 초기화하고, 실제 Spawn 성공 시 적의 실제 KindId를 관측 집합에 추가한다. 예정과 다르게 실제로 나타난 종류도 웨이브가 끝날 때까지 보존한다. 그 적이 틱 사이에 나타났다가 죽어도 이후 조회에서는 해당 종류가 0으로 남는다.

기존 `CaptureAliveSnapshot(center, radius, plannedKinds)`는 이 집합으로 0을 먼저 채우고 기존 alive 목록의 파괴되지 않은/IsDead가 아닌 적만 한 번씩 더한다. AddAlive가 같은 값 스냅샷의 종류별 수와 총합을 함께 증가시킨다. 틱 경로는 `CaptureAliveSnapshot(null, null, null)`을 한 번만 호출하며 별도의 AliveCount를 읽지 않는다. 전역 FindObjects·전체 씬 검색은 없다.

실제 처치로 목록에서 빠지거나 Stop으로 강제 제거되면 다음 스냅샷의 생존 수는 줄어든다. Stop은 종류 이력을 유지하므로 같은 웨이브의 빈 목록은 기존 종류들의 0으로 해석된다. 다음 Begin은 이전 웨이브의 예정/실제 종류를 모두 초기화하므로 무관한 종류가 다음 웨이브로 넘어가지 않는다. 강제 제거를 처치로 집계하지 않는 기존 게임 규칙은 유지한다.

2차 사망 경로도 같은 CaptureAliveSnapshot API를 사용한다. center와 유효 반경이 있을 때만 실제 월드 거리의 반경 내 수를 계산하며, 정리 전 조회/출력 순서는 유지한다. 순수 집계 모델이 실제 Unity 적 목록을 대신 관리하거나 적 생성·제거를 지시하지 않는다.

## 후속 API

- `LogSession.FixedTick`, `LogFixedClock.TickCount`: 공통 시계가 증가시킨 실제 고정 틱 상관 번호.
- `LogFixedTickCollector.CanRecord(bool controllable)`: 세션·단계·새 틱·저장 상태를 확인한다. Unity 상태 조회 전에 사용한다.
- `LogFixedTickCollector.Record(bool controllable, LogPlayerTickSnapshot player, LogEnemySnapshot enemies)`: 시간을 더하지 않고 두 레코드를 기록한다. 스냅샷을 먼저 값 복사/검증하고 같은 틱 중복 호출을 거부한다.
- `LogEnemyPopulation.Reset/ObserveKind/CreateSnapshot/AddAlive`: WaveController가 소유하는 예정/실제 종류 이력과 순수 스냅샷 집계. 호출 순서는 실제 Begin/Spawn/현재 생존 목록을 따른다.
- `PlayerMovement.IsControlEnabled`, `PlayerWeapon.AimCamera`: 관측 전용 getter.

전투·탄약·슬롯·상점 집계는 여전히 후속 차수다. fixedTick 수집 자체가 combat/ammo 요약을 수집 완료 상태로 바꾸지 않는다.

## 검증과 사용자 확인

`.omo/verification/log-phase3/RESULTS.md`에 재실행 명령과 결과를 기록했다. 1,000개의 조작 가능한 합성 고정 틱에서 각 1,000개 레코드와 모든 쌍의 경과 시간·번호·sequence를 확인했고, 별도 실제 파일 저장소의 합성 JSONL도 파싱했다. 이 입력에는 실제 Unity 렌더 프레임이나 충돌이 없으며, 연속된 여러 고정 틱 입력이 렌더 프레임에 의해 필터되지 않는 계약을 검사했다. 실제 Unity 스케줄링·컨트롤러 동작·표시 각도·프레임 비용은 검증하지 않았다.

사용자 Unity 확인 절차:

1. 새 순수 C# 소스 2개와 meta를 import하고 컴파일 오류를 확인한다. Preload→Title→Game으로 시작해 persistentDataPath/Telemetry의 해당 세션 파일을 연다.
2. 이동하지 않는 상태에서도 매 조작 가능 고정 틱에 player_position/enemy_alive_counts 한 쌍이 생성되는지 확인한다. fixedTick·elapsedSeconds는 같고 sequence는 구분돼야 한다. 실제 FixedUpdate 횟수와 비교한다.
3. 이동·시점 회전·단일 무기/아킴보·휴대 슬롯 변경 시 월드 x/z, 실제 카메라 Euler 각도, 슬롯/좌우 손/개체 ID를 비교한다. 무기 바닥 왕복 후에도 해당 개체 ID가 유지되는지 확인한다.
4. 슬롯 회전 중 이동하고 적을 조기 전멸시킨 뒤 남은 시간에도 움직인다. 같은 틱 쌍이 계속 나와야 하고 전멸 종류는 0이어야 한다. 예정 종류는 스폰 전에도 0으로 남아야 한다.
5. 상점·입력 차단·이동 컴포넌트/CharacterController 비활성 상태에서는 위치/적 수가 생성되지 않는지 확인한다. 상점에서도 세션 경과 시간은 이어져야 한다. 테스트 중 변경한 활성 상태를 복원한다.
6. 사용자 테스트에서 Time.timeScale을 정지/재개하고 실제 Time.fixedDeltaTime도 바꿔 본다. 정지 중 추정 기록이 없고 재개 후 실제 틱부터 이어지는지 확인한 뒤 설정을 복원한다. 같은 렌더 프레임에 여러 FixedUpdate가 실행되는 조건에서도 틱이 각각 남아야 한다.
7. 다음 웨이브의 종류 집합이 새 예정/실제 종류로 바뀌고 이전 종류가 섞이지 않는지 확인한다. 사망하면 틱 쌍은 멈추고 2차 정리 전 사망 스냅샷/중단 요약/세션 종료 순서는 유지돼야 한다.
8. 사용자 환경에서 파일 flush와 장시간 기록량/프레임 영향을 확인한다. 버퍼링이나 flush 간격을 틱별 샘플 간격으로 해석하면 안 된다.

`Docs/로그-시스템-3차.synthetic.jsonl`은 실제 FileLogStore로 만든 합성 입력 예시이며 실제 플레이 로그가 아니다. synthetic-* 맵/무기/적, 주입한 UTC, 테스트 좌표를 사용한다. 1·2차 회귀 검사 실행으로 해당 단계의 합성 샘플도 재생성했다.
