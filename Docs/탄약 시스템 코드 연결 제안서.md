# 탄약 시스템 코드 연결 제안서

## 목적과 범위

`탄약 기획안.md`에 따라 탄종별 예비탄을 도입하기 위한 후속 구현 안내다. 이번 작업은 `POC2/Assets/Resources/AmmoData.json` 작성까지이며, 게임 코드 연결은 아직 하지 않았다. 기획에서 정하지 않은 사항은 아래의 제안 또는 결정 필요 항목으로 구분한다. `작업지침.md`의 JSON 테이블, TableManager, UI MVP 및 프리팹 규칙을 따른다.

## 작성된 테이블

`AmmoData.json`의 `ammoTypes` 항목은 `id`, 표시명 `name`, 대표색 `color`(HTML hex), 기준 탄창 크기 `referenceMagazineSize`, 장전탄을 제외한 예비탄 최대 `maxReserve`와 시작량 `startingReserve`를 가진다. 색상은 임시값이다. 기준 크기는 현재 `WeaponData.json`의 리볼버 6, 볼트액션 5, 기관단총 30과 기획안의 샷건 2를 사용했다. 각 최대량은 기준 크기 × 10, 시작량은 × 6이다. 따라서 권총은 60/36발이다. 기획안의 권총 최대 72발 예시는 × 10과 충돌하므로 계산식을 우선한 임시 해석이다.

기준 탄창 크기는 탄종의 고정 기준으로 제안한다. 같은 탄종의 다른 무기가 추가되어도 예비탄 최대량이 무기 교체에 따라 흔들리지 않는다. 값은 초기 테이블 기준이고 추후 최대량 업그레이드는 실행 중 상태에 별도로 반영한다. 현재 JSON은 Unity가 아직 읽지 않으며 `status`는 잠정값 표시다.

## 코드 변경 지점

1. **데이터 로드 및 검증**: `Assets/Scripts/Data/AmmoData.cs`에 JSON 필드와 일치하는 순수 직렬화 클래스를, `Assets/Scripts/Info/AmmoInfo.cs`에 ID 조회 및 검증을 추가한다. `Assets/Scripts/Core/TableManager.cs`에 `Ammo` 프로퍼티, `Load<AmmoData>(nameof(AmmoData))`, 검증 호출을 추가한다. 중복·빈 ID, 잘못된 색상, 음수, 시작량이 최대량을 넘는 경우와 무기/상점의 존재하지 않는 탄종 참조를 검증한다. `JsonUtility`가 읽을 수 있도록 기존 테이블처럼 공개 필드와 배열을 사용한다.
2. **무기와 탄종 연결**: `WeaponData.json`, `Data/WeaponData.cs`, `Info/WeaponInfo.cs`에 `ammoId`를 추가하고 리볼버→`pistol`, 볼트액션→`sniper`, 기관단총→`smg`로 연결한다. 샷건은 무기 구현 시 연결한다. `Game/GameManager.cs`의 `ApplyWeapon`에서 현재 탄종을 `Player/PlayerWeapon.cs`에 전달한다. 같은 탄종 무기는 같은 예비탄을 참조한다.
3. **예비탄 상태**: `Assets/Scripts/Model/AmmoInventory.cs`를 신설해 탄종별 현재 예비탄과 변경 가능한 최대량을 보관하고 시작량으로 초기화한다. 조회, 최대량 제한을 적용한 추가, 실제 소비량 반환, 최대량 변경과 변경 이벤트를 제공한다. `GameManager`가 게임 시작마다 소유·초기화하고 무기, UI, 상점, 픽업에 동일 인스턴스를 연결한다. 장전탄은 기존처럼 무기별로 보관한다.
4. **재장전**: `PlayerWeapon.StartReload`에서 예비탄 0이면 재장전을 막고, 완료 시 부족한 탄과 예비탄 중 작은 수량을 이동하는 방식을 제안한다. 취소 시 이동하지 않는다. `RefillImmediately`는 현재 재장전 완료와 슬롯 보상이 함께 호출하므로 두 동작을 분리하고, 슬롯 보상 정책은 결정 후 연결한다. `Configure` 및 `GameManager`의 무기 구매·바닥 무기 교환에서는 장전탄 보존과 탄약 생성 정책을 명시적으로 적용한다.
5. **적 드롭**: `EnemyWeaponData.json`과 `Data/EnemyWeaponData.cs`에 드롭 탄종 참조를 추가하는 방안을 제안한다. `Wave/WaveController.cs`는 스폰 시 무기를 `Enemy.Configure`에 전달하고, `EnemyKilled` 이벤트를 발행한다. `Enemy/Enemy.cs`에서 처치 시 해당 무기 탄종을 조회할 수 있도록 노출하고, 처치 이벤트를 받는 곳에서 탄약 픽업 프리팹을 생성한다. `WaveController.Stop`은 적을 처치 이벤트 없이 제거하므로 종료 정리에서 드롭이 발생하지 않게 유지한다. 무기 없는 적과 각 적 무기의 탄종 매핑은 기획 결정이 필요하다.
6. **획득 및 정리**: 탄약 픽업 컴포넌트와 프리팹을 추가해 색상·탄종·수량을 표시하고 접근 시 `AmmoInventory`에 추가한다. 기획의 반 탄창은 기준 크기를 사용할 것을 제안하며 홀수 반올림과 최대량 도달 시 잔여 아이템 처리는 결정이 필요하다. `GameManager`의 웨이브 종료→상점 전환 지점에서 탄약 픽업만 정리한다. 기존 바닥 무기 픽업은 별도로 유지한다.
7. **상점**: `Resources/ShopData.json`, `Data/ShopData.cs`, `Info/ShopInfo.cs`에 탄약 구매 타입 및 탄종별 항목을 추가하고 가격을 데이터화한다. `GameManager.TryBuy`에서 상점 단계, 잔액, 최대량 여부를 확인한 뒤 결제와 보충을 처리한다. `UI/ShopPresenter.cs`가 잔여량과 구매 가능 상태를 갱신하고 `UI/ShopView.cs` 및 상점 프리팹에 네 칸이 들어갈 공간을 마련한다. 가격은 미결정이므로 임의 확정하지 않는다.
8. **HUD와 슬롯**: `UI/HudPresenter.cs`가 현재 탄종 예비탄 및 변경 이벤트를 전달하고 `UI/HudView.cs`와 HUD 프리팹에서 장전탄/예비탄, 재장전 및 탄약 부족을 표시한다. `Slot/SlotMachinePresenter.cs`는 현재 `RefillImmediately`를 호출한다. 슬롯 탄약 심볼이 예비탄을 소비하는지 생성하는지와 탄약 퍽 효과를 확정한 뒤 별도 보상 경로로 연결한다.

## 구현 전 결정 필요

- 적 머스켓·WWI 소총·WWII 소총 각각의 드롭 탄종, 무기 없는 러셔의 드롭 여부, 드롭 확률.
    -> 러셔는 드랍하지 않는다. 사격하는 적은 musket 시대엔 권총 탄약, WWI 이후엔 저격 탄약을 드롭한다.
- 5발 탄창의 절반 반올림, 최대량일 때 획득 여부 및 일부만 들어갈 때 잔량 처리, 획득 거리.
    -> 최대 탄약이 100발이고, 플레이어는 95발을 보유중이다. 탄약 회복량이 5를 넘어섰다면 100까지만 회복된다. 또한, 최대 상태일 땐 탄약을 줍지 못한다.
- 탄종별 상점 가격과 미보유 무기의 탄약 구매 허용 여부.
    -> 상점 가격은 모두 200원이다. 미보유 무기 탄약도 구매 가능하다.
    
## 후속 검증 시나리오

- 테이블 로드 및 네 탄종의 ID·수치·참조 검증, 새 게임 초기화와 최대량 업그레이드 확인.
- 예비탄 0, 부족, 충분 상태에서 재장전과 중도 취소; 같은 탄종의 무기 간 공유 및 바닥 무기 장전탄 보존.
- 적 처치 시 정해진 탄종·수량 드롭, 상한 근처 획득, 웨이브 종료 정리와 무기 픽업 보존.
- 상점에서 잔액 부족·최대량·정상 구매 및 HUD 즉시 갱신; 슬롯 보상과 퍽의 확정된 정책 확인.
- Unity에서 실제 게임 플레이로 재장전, 획득, 상점과 UI를 확인하고 기존 무기 교체·웨이브 검증도 실행한다.

재장전과 슬롯은 현재 `PlayerWeapon.RefillImmediately`를 공유하므로 같은 작업에서 분리한다. 드롭과 상점은 공유 모델 위에 각각 월드 프리팹과 상점 UI를 연결하므로 작업을 나눈다. 마지막 작업은 저장된 씬 연결과 실제 플레이를 확인한다.

### 현재 확정 기준과 남은 해석

아래는 최신 기획과 위 답변을 반영한 실행 기준이다. 앞부분의 권총 72발, 상점 가격 미정, 러셔 드롭 미정이라는 초기 설명보다 우선한다.

- 최대 예비탄은 기준 탄창 × 10, 시작 예비탄은 × 6이다. 장전탄과 별개이며 권총 60/36, 저격 50/30, 기관단총 300/180, 샷건 20/12다. 시작 리볼버는 별도로 6발 장전한다. 모든 탄종의 시작 예비탄을 지급한다.
- 모든 무기는 최초 획득 시 장전돼 있다. 바닥 무기 재획득은 기존에 보관한 장전탄을 이어받는다.
- 사격하는 적의 드롭 탄종은 머스켓 시대 `pistol`, WWI 이후 `sniper`다. 러셔는 드롭하지 않는다.
- 픽업 수량은 해당 탄종 기준 탄창의 절반이다. 획득량은 최대 예비탄을 넘지 않으며 최대량에서는 줍지 못한다. 상점 진입 시 남은 탄약 픽업을 정리한다.
- 상점은 네 탄종 각각 200원으로 현재 최대 예비탄까지 보충한다. 미보유 무기 탄약도 구매할 수 있다.
- 슬롯은 들고 있던 총의 탄창 하나를 회복하며 보급량 2배는 구현하지 않는다. 기존 탄약 퍽의 등장 가중치 효과는 유지한다.
- HUD는 좌측 하단에 `장전탄 / 예비탄`, 상점 좌측에는 네 탄종의 보유량을 표시한다. 샷건은 탄종만 준비하며 무기는 추가하지 않는다.

아직 명시되지 않은 항목은 1차에서 사용자에게 묶어서 확인하고 답변을 여기에 기록한다. 답변을 기다리는 동안 정책과 독립적인 기반 작업은 진행할 수 있지만, 미확정 정책에 의존하는 코드를 임의로 확정하지 않는다.

- 드롭 확률: 모든 사격 적이 항상 드롭하는지.
- 저격탄 반 탄창 2.5발의 정수 처리, 일부 획득 후 초과분 소멸/픽업 잔량 유지, 자동 획득 거리와 벽 너머 획득 허용 여부.
- 슬롯의 '탄창 하나 회복': 탄창 부족분을 무료로 채우는지, 예비탄에 한 탄창을 더하는지. 지급 대상은 회전 시작/지급 시점 중 어느 무기인지. 재장전 도중 보상 처리.
- 같은 무기 재구매 시 새 장전탄을 지급하는지, 최대 예비탄 감소 시 초과분을 버릴지.

### 공통 작업 규칙

- 매 작업 시작 시 `Docs/작업지침.md`, `Docs/탄약 기획안.md`, 이 문서와 이전 작업 진행 기록을 읽는다. 과거 예비탄 무한 규칙보다 최신 탄약 기획을 따른다.
- 확정 수치는 JSON → 순수 Data → Info → TableManager로 관리한다. UI는 MVP·저장된 프리팹으로 구성하며 런타임 UI 생성은 하지 않는다.
- Allman 중괄호, 파라미터 `_` 접두사 등 프로젝트 스타일과 Unity `.meta`·직렬화 참조를 지킨다.
- 슬롯 중 자유 시점·이동·사격, 발사체, 적 시대 진행, 처치 보상·생존 보너스, 바닥 무기 장전탄 보존과 패드 줍기 우선순위를 유지한다.
- 씬 전체 재생성으로 기존 작업을 덮어쓰지 않는다. 선택적 저작 방식을 활용하고, 열려 있는 Unity의 미저장 씬을 강제로 저장하거나 덮어쓰지 않는다.
- 각 프롬프트의 검증을 수행하고 실행 결과와 정적 확인을 구분한다. 실행 환경이 없으면 미검증 사유를 기록한다. 커밋·푸시는 별도 요청 없이 수행하지 않는다.

### 1차 작업 프롬프트 — 데이터·공유 예비탄 기반

```text
TrenchSlot 탄약 시스템 연결 1차 작업을 수행해줘. 실제 Unity 프로젝트는 POC2/다.
```
